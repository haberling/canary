# Canary — Website Framework

## What Canary is

Canary is a standalone C# website framework, distributed as a native-feeling CLI tool (`canary`/`canary.exe`). A "Canary site" is a directory containing a JSON project configuration file plus content (markdown) and theme assets; `canary build`/`canary serve` operate on that directory the same way for any site that adopts it — consoland included, eventually, but consoland is now a *consumer* of Canary, not the thing Canary is extracted from and tied to.

This supersedes the original framing of "split the framework pieces out of consolandWebsite." That extraction is still where the initial code comes from (see **Origin**, below), but the target is a general-purpose tool, not a one-off migration.

## Origin (institutional memory, not the current goal)

Canary began as a plan to split consolandWebsite's hand-rolled TypeScript runtime (hash router + markdown renderer + nav-from-manifest) and C# build/deploy tooling out from that site's actual content and branding — motivated by wanting the markdown-wiki site to be crawlable without losing its "no framework" hand-built character.

**Why hash routing existed in consoland in the first place**, worth carrying forward: GitHub Pages is pure static file serving with no server-side rewrites available (short of the "404.html redirect" trick). Hash routing needs zero server config — any request loads `index.html`, and the fragment after `#` is never even sent to the server, so client-side JS alone decides what renders. That's still a mode Canary needs to support well; it's just no longer the *only* mode.

## Distribution & consumption model

Canary should feel like a native CLI tool to use — `canary build`, `canary serve`, `canary.exe build` on Windows — not something invoked through `dotnet tool run` ceremony. Long-term intended distribution channel is **winget**, not a NuGet/`dotnet tool install` package; calling `dotnet tool run` for every invocation was explicitly rejected as unnatural. That preference should inform build/publish choices later (e.g. self-contained or Native AOT single-file publish, so end users don't need the .NET SDK/runtime preinstalled just to run it) — but that's a later-phase concern, not something to solve now.

For now, **local/source-only**: build and run Canary from source while it's this early. No public package (winget or otherwise) published yet — revisit once the CLI surface has stabilized through the phases below.

## Architecture: two layers

1. **C# core (the CLI/build engine)** — config loading, manifest generation, prerendering, incremental builds, output writing, sitemap/robots generation. This is Canary's actual product.
2. **Vendored client runtime (TypeScript, compiled to JS)** — the real-path client router, nav population, and content widgets (download links, slideshow) that run in the visitor's browser. This still needs a TS toolchain to *develop*, but is pre-compiled and embedded into the Canary package at release time — a site author consuming Canary never runs `npm`/`node` themselves.

### Client runtime packaging

- TS source lives in Canary's own repo (e.g. `runtime/ts/`) and is compiled to JS via the existing npm-based toolchain, but only as part of *Canary's own* release/build process.
- The compiled output gets embedded into the Canary package (as embedded resources in the C# project, or similar) and written out to each site's build directory by `canary build`.
- Net effect: **zero Node dependency for anyone consuming Canary**, Node only matters if you're developing Canary itself.

## Render modes (config-selectable, not one-size-fits-all)

Original consoland decision was hybrid-only: prerender to real static paths *and* keep the hash-router SPA layer for in-app nav. Generalizing this for arbitrary sites, `renderMode` is a config field with two values. Both modes still run JS for nav population (`loadNav()` reading `manifest.json`, same as today) and for widgets (slideshow, downloads) — "how much JS runs" isn't what distinguishes them. What actually differs is **how in-app navigation happens** — both modes are fully prerendered; markdown→HTML always happens at build time, the browser never sees markdown source in either one:

- **`hybrid`** (what consoland needs) — a real prerendered HTML file exists per route, so cold loads (crawlers, direct links, social-preview scrapers) get real content immediately. For in-app navigation once JS has loaded, the router intercepts the click and **fetches the target route's own prerendered HTML file, extracts the `<main id="app">` fragment via `DOMParser`, and splices it into the DOM** — no full reload, and critically, no re-rendering. It's the same file, same bytes, whether you arrive cold or navigate in warm. Raw markdown is never shipped to or parsed by the client in this mode. **Navigation is keyed off the real path via the History API (`pushState`/`popstate`), not a hash fragment** — see **Resolved** (2026-08-20) for why the router was switched from hash-based to real-path.
- **`static`** — same prerendered HTML files as hybrid, but no router/content-swap layer at all. Every internal link is a real `<a href="/games/tesselate/">` href; every navigation is a full page load, handled by the browser/server, not JS. Nav and widgets still run as page-enhancement JS.

**A third mode, `spa`, existed from Phase 1 through 2026-08-18 and was removed.** It shipped raw markdown to the client and rendered it there via a dedicated client-side markdown renderer (`runtime/ts/markdown.ts`) and router (`spa-router.ts`) — no prerendered per-route files at all, closest to consoland's original pre-Canary behavior. It was cut once designing the **Content toolchain** made its remaining justification collapse: a toolchain tool can only ever run at build time (arbitrary external command, no browser equivalent), so `spa` would have had to prerender to get the toolchain working anyway — at which point it was no longer meaningfully different from `hybrid` in *how content gets built*, only in navigation policy. See **Resolved** for the full removal reasoning. (Its hash-only-navigation UX was briefly considered recoverable as a `hybrid` config flag — see the now-superseded entry in **Resolved**, 2026-08-20 — but hash routing itself is gone from Canary entirely now, so that idea no longer applies to anything.)

## Core built-in functionality (absorbed from consoland's tools)

`tools/build-manifest.cs` and `tools/deploy.cs` are not going to survive as separate opt-in files a site has to wire up — their functionality (manifest/nav generation, incremental build) is core enough that it becomes **built into the Canary executable itself**, generalized away from consoland specifics (no hardcoded domain, no baked-in CNAME, no consoland branding assumptions).

**What "deploy" actually reduces to.** The real end goal across all render modes is a website that lives on a file server — Canary's job stops at producing correct output in a configurable output folder (`output.dir`, defaulting to `docs` for GitHub Pages' "serve from `/docs` on main" convention). For a git-based static host like GitHub Pages, that's the *entire* deploy story: `canary build` writes to `docs/`. No bespoke GitHub-specific deploy step is needed.

**Revised 2026-08-21 — Canary now can commit/push, or FTP, or anything else, but only because the site author told it to, never because it has an opinion about how sites get deployed.** The original stance above ("Canary shouldn't be auto-committing/pushing") held right up until `canary publish` (see **Publishing** below): a single arbitrary external command a site author writes and registers themselves, same "just run whatever's there" philosophy as a toolchain tool. This isn't a reversal of "no built-in deploy-target abstraction" — it's the same anti-abstraction stance applied consistently: Canary still doesn't understand git, FTP, or rsync, and never will; it just runs a command. That also quietly retired the standalone "remote push mechanism (FTP/SFTP)" idea below — a site author gets that today by writing an FTP/SFTP one-liner as their own `publish` command, no Canary-side FTP/SFTP client ever needed.

## Plugin system — cut from scope (for now)

Originally planned as build-time C# extensibility via Roslyn scripting (a site-supplied `.cs` file, run in-process, direct access to Canary's build objects). **Deliberately axed for now** — premature to design an extension mechanism before the core it would extend even exists. If a real need shows up once Phases 0–3 are built, revisit then with an actual use case driving the hook points, rather than speculating about them now. Not on the phase list below.

This has no bearing on **widgets** (client-side/browser-executed JS — download links, slideshow), which remain part of the vendored runtime regardless.

## Widget system — resolved controversy (2026-08-17, two rounds)

Widgets went through a real design fight, captured in full in `MostImportantControversy.md`. Short version: reviewing the ported `SlideshowWidgetRenderer.cs` surfaced a real bug (`RenderSlide` never called `ResolveUrl`), which turned into the real objection — hand-porting every widget to C# means two independent implementations of the same thing, which is exactly how that bug (and the earlier double-escape bug) happened.

**Round 1** (superseded, kept here for history): widgets as plain `.js` files with a `render(title, body) -> string` export, executed at build time via **Jint** (embedded JS interpreter). This fixed the "two implementations" problem but not the actual complaint — `render()` still contained real procedural HTML-construction logic (string concatenation, conditionals for the link-vs-copy-command branching). Moving the code from C# to JS didn't make it not-code.

**Round 2 (final): widgets are declarative, not code, on either side.**
- **A widget is an `.html` file (real Mustache-syntax template) plus an optional `.js` file (shared client-side behavior, only needed if the widget is interactive).** The fence block's body is real **YAML**, not the old ad-hoc `label | url` shorthand. Both are hand-rolled implementations (no external library dependency) but *real*, standard syntax — Mustache and YAML are language-agnostic specs with implementations in dozens of languages (`mustache.js`, `Stubble.Core`, etc.); using the real syntax means anyone who's used either before can read/write a Canary widget with zero Canary-specific knowledge, even though our own parser/templater are one-off.
- **`Canary.Core.Templating`**: hand-rolled `YamlParser` (a practical subset — block mappings, lists of mappings, scalars; no flow style/anchors/multi-line block scalars) and `MustacheTemplate` (`{{var}}` HTML-escaped, `{{#section}}`/`{{/section}}`, `{{^section}}`/`{{/section}}`; no partials, no unescaped output, no lambdas). `Canary.Core.Widgets.TemplateWidgetRenderer` is the entire "renderer" now — parse YAML, fill the template, done. **Jint is gone entirely** (removed from `Canary.Core.csproj`) — there's no more widget-authored code to execute at build time.
- **Interactivity moved from "generated once per instance" to "one shared script, referenced once per page."** The old approach regenerated the *entire* click/keydown/autoplay JS as a string on every single widget occurrence (visible in the raw HTML as sprawling inline `onclick=` attributes). Now a widget's template emits plain, data-only markup (`data-widget="slideshow"`, real `<img>` tags, no inline JS at all), and its `.js` file (if any) is copied once and referenced via `<script src="/js/widgets/<name>.js" defer>` — real, boring, readable JS using `document.addEventListener` with event delegation, not string-templated code. A newly-swapped-in widget instance (hybrid mode's fragment-fetch) is handled automatically by delegation; the one thing delegation can't cover (autoplay start on first image load, hiding nav for a single-slide show) uses a `MutationObserver` — the standard way to react to dynamically-inserted DOM content.
- **Discovery, not registration**, same principle as round 1: `SiteBuilder` scans `runtimeDistDir/widgets/` (built-in) and `<siteRoot>/widgets/` (site-authored, takes precedence on a name collision) for `*.html` (templates) and `*.js` (behavior) separately, keyed by filename. No config entry — reference the fence tag in content, and if a matching template exists, it's used. A page's shell gets a `{{widgetScripts}}` placeholder (new, alongside `{{title}}`/`{{content}}`/etc.) filled with `<script>` tags for every discovered behavior script, site-wide (v1 simplicity: every page references every widget's script if one exists anywhere on the site, not just pages that use it — a few extra small requests on pages that don't need a given widget, traded for zero per-page usage-tracking complexity).
- **Found and fixed two more real bugs by actually running things, not by review:** (1) the shell.html self-collision bug repeated itself — `downloads.html`'s own explanatory comment used literal `{{#items}}` syntax as documentation, which the templater dutifully executed as a real tag, corrupting output; fixed by describing the syntax in prose instead of writing it literally. (2) `ResolveUrl` was a genuine gap: with no widget-specific code left anywhere, nothing applied the root-relative-path fix to a YAML `url:`/`src:` field. **Resolved 2026-08-17**, same day: the user explicitly didn't want automatic field-name-based resolution ("not that interested in non-url fields being resolved by an automated system... a syntactical rule must be made"), so instead of guessing, an author opts in explicitly with a real YAML tag: `url: !url "content/games/x.png"`. `Canary.Core.Templating.UrlResolver` now holds the one shared implementation (extracted out of `MarkdownRenderer`, which used to have its own private copy — one implementation, not two, same principle as everywhere else in this section); `YamlParser` detects the `!url` tag on any scalar (top-level or inside a list item) and resolves it at parse time, before the value ever reaches the Mustache templater. A plain `url:`/`src:` with no tag is left untouched. Both widget templates' doc comments updated to show the tag; regression/unit-tested (`YamlParserTests`) and end-to-end tested through the real `SiteBuilder` pipeline (`SiteBuilderWidgetDiscoveryTests`).
- Verified end-to-end: real build against the `workspace/` dogfood site, real browser testing via claude-in-chrome (slideshow prev/next/autoplay-pause, downloads copy-button, all via the shared delegated scripts, zero console errors), plus unit tests for `YamlParser`/`MustacheTemplate` and an integration test proving the actual promise — a throwaway custom widget dropped into a test site's `widgets/` folder is picked up and rendered with zero registration, and its behavior script gets copied + referenced automatically.

**Still open:** whether `{{widgetScripts}}` should become per-page (usage-tracked) instead of site-wide. (Two other items that used to be listed here — client-side widget rendering for `spa` mode, and making the `!url` tag consistent between build-time and `spa` client-time — are moot now that `spa` mode has been removed entirely; see **Render modes**.)

**`canary widgets` / `canary widget <name>` CLI commands (2026-08-17).** Every widget's `.html` file now has a dedicated `<!--clipboard ... -->` comment block (separate from its main documentation comment) holding a ready-to-paste fence-block usage example — inferred from the request itself (the user asked for the marker before saying what it was for) as the reason for wanting one: a CLI command to look up a widget's usage without digging through its source. `canary widgets` lists discovered widget names (built-in + site-authored, via the same `Canary.Core.Widgets.WidgetDiscovery` now shared with `SiteBuilder` — extracted out to avoid a third copy of the discovery rule); `canary widget <name>` prints that widget's clipboard example via `Canary.Core.Widgets.WidgetClipboardExample`. **Print-only, not real OS clipboard** — deliberate: there's no cross-platform clipboard API in .NET itself (real clipboard access means either a Windows-only dependency (WinForms/WPF) or shelling out to a different tool per OS, with Linux not even having one universal option between X11/Wayland). A user who wants their real clipboard can pipe the output themselves (`canary widget slideshow | pbcopy` etc.) — Canary doesn't need to own that. Confirmed cross-platform-targetable while at it: both `.csproj` files target plain `net10.0` (not `net10.0-windows`), and nothing in the codebase (`HttpListener`, `FileSystemWatcher`) uses a Windows-only API — not yet actually run on Linux/macOS to verify, but nothing should block it.

**Bug found via user review of the live dogfood site, not by me:** the downloads widget's copy-command row had lost its `.copy-command-row` wrapper `<div>` during the template rewrite — `<code>` and the Copy `<button>` became direct children of `.copy-command` (a flex *column* container), so they stacked vertically instead of sitting side by side per `framework.css`'s `.copy-command-row` flex-row rule. Fixed by restoring the wrapper.

**That fix surfaced a real, more significant gap in the incremental-build system**, found while re-verifying it: `canary build` initially reported "reused unchanged = 6" after the template fix — the checksum-gating in `PageBuilder`/`SiteBuilder` only hashes the *markdown source*, never the widget template/behavior files a page's content references. Editing a widget's `.html`/`.js` does not invalidate the cache for pages that use it; only a full rebuild (or editing the markdown itself) picks up a widget change. Worked around here by clearing `output.dir` and rebuilding clean at the time — **fixed properly 2026-08-18, alongside implementing the Content toolchain (see that section)**, rather than left open.

**Widget CSS extracted out of `framework.css` into per-widget `.css` files (2026-08-18), caught by user review of the CSS itself.** The built-in `downloads`/`slideshow` widgets' styling had been hardcoded directly into the site's base `framework.css` since before this round's redesign even existed — which quietly broke the "built-in and site-authored widgets are discovered and treated identically" promise everything else in this section was built around: a site-authored widget had no equivalent place to put its own CSS, while the two built-ins got free styling nobody else could get. Fixed by giving widgets a third discovered file type alongside `.html`/`.js`: `runtime/widgets/downloads.css`/`slideshow.css` (extracted verbatim, no rule changes — they reference the same `--bg`/`--accent`/etc. tokens `framework.css` defines on `:root`, which cascade globally regardless of which linked file references them, so nothing needed to change functionally), `Canary.Core.Widgets.WidgetDiscovery` gets a third `"*.css"` call, `SiteBuilder` copies discovered stylesheets to `output/css/widgets/<name>.css` and fills a new `{{widgetStyles}}` shell placeholder with `<link>` tags (same site-wide-not-per-usage pattern as `{{widgetScripts}}`), and the widget checksum seed now covers `.css` too. `copy-widgets.mjs` updated to also copy `.css` into `runtime/dist/widgets/`. Verified: 129/129 tests (2 new, mirroring the existing `.js` coverage), and a real rebuild + browser check of `workspace/` confirming both built-in widgets render pixel-identical to before — the fix is purely about *where* the CSS lives, not what it says.

**Deliberately not done:** redesigning *how* a widget authors its interactivity (the inline `onclick`/`onload` string-building pattern itself is still hand-rolled JS-as-strings, just now in one place instead of two) — that was explicitly flagged as a separate, larger question and left alone for now.

**A third built-in widget, `code` (2026-08-21)** — `runtime/widgets/code.{html,css}`, no `.js` (static, not interactive). Renders a `lines` list (each entry a one-field `{ text: "..." }` map) back out as an escaped, verbatim `<pre><code>` block, with an optional cosmetic `lang` label. Built specifically to answer "how do I show a widget's own fence syntax as literal example text instead of it running as that widget" — no escape sequence exists for a fence's info string otherwise (`` ```downloads `` always dispatches to the `downloads` widget). See **Documentation site** below for the full story, including a real `YamlParser` quoting gotcha found writing its own example.

## Content toolchain — per-page markdown preprocessing (implemented 2026-08-18, renamed to "toolchain" 2026-08-21)

Motivating case, from the user: functionality that should apply to *many* pages — a breadcrumb at the top, a "Return to Blog" link at the bottom of every post — without copy-pasting a widget fence block into every markdown file. Doing that in the content itself defeats the actual goal, keeping site behavior and content data separate (same spirit as why widgets exist at all). A **tool** is an external command that receives a page's raw markdown on stdin and returns transformed markdown on stdout, run once per page at build time, before that markdown reaches the renderer.

**Why build time, not per-request/in-browser:** a toolchain tool is an arbitrary external command — no browser equivalent exists, so it can only ever run once, at build time, before the transformed markdown reaches the renderer. This was actually the realization that killed off `spa` mode entirely (see **Render modes**, **Resolved**): `spa` used to ship raw markdown to the client and render it there, which would have meant either giving the toolchain a client-side escape hatch that doesn't make sense for an arbitrary external command, or `spa` prerendering anyway and losing its own reason to exist. With `spa` gone, the toolchain only ever needs the one `hybrid`/`static` prerendering path that already exists — no second code path to keep in sync, no "does this also need a JS port" question to re-litigate for every future feature.

**`.toolchain.json` auto-creation goes deeper than `.nav.json`'s does.** `.nav.json` only auto-creates at *top-level* content directories, because `ManifestBuilder.BuildNav` only ever walks one level deep — nav's data model is flat categories with children, so that's all it needs. The toolchain has no such shortcut: since application is deliberately non-recursive with no inheritance (see above), a directory's tool list only ever covers `.md` files directly inside it, at *any* depth. So `.toolchain.json` auto-creation has to mirror `ContentScanner`'s full recursive walk (`SearchOption.AllDirectories`), not `ManifestBuilder`'s one-level walk: every directory containing at least one `.md` file directly inside it, at any depth, gets an empty self-documenting `.toolchain.json` if missing — same backfill-on-missing-fields behavior `.nav.json` already has, just scoped deeper.

**Registry (definition) vs. application are deliberately separate concerns:**
- **Definition** — a `tools` dictionary (name → command) in `canary.json`, alongside `site`/`content`/`theme`/`widgets`. One central place, since this part genuinely is site-wide, not per-directory.
- **Application** — a new **`.toolchain.json`** per content directory, sitting alongside `.nav.json` but a **separate file**, not a section bolted onto it. Considered and rejected merging into `.nav.json`: nav visibility and tool application are orthogonal axes, the same reasoning already applied in Phase 3 to keep `SitemapBuilder` independent of the nav tree ("nav visibility and search-engine discoverability are independent axes, not the same thing"). Merging would also mean `ManifestBuilder` (which owns `.nav.json`'s read/backfill/self-documentation today) either has to learn about the toolchain, or some other module has to co-own that file's schema for fields it doesn't otherwise touch — and `.nav.json`'s name would quietly stop meaning what it says.
- **No cascading/inheritance down the content tree.** A directory's tool list is exactly what its own `.toolchain.json` declares — nothing inherited from a parent directory. Considered and rejected inheritance explicitly: it's the same implicit-behavior problem already resolved once for widgets (the `!url` tag decision) — a page's behavior shouldn't depend on something declared three directories up that isn't visible from where the page actually lives. The tradeoff is real repetition for a tool meant to apply broadly (re-declaring `"breadcrumb"` in every directory that wants it), accepted deliberately in favor of every directory's behavior being visible without tracing up the tree.

**Execution model:** a page's applicable tool names run in their declared array order, chained — one tool's stdout becomes the next one's stdin, and the final result is what the renderer sees. A tool command exiting non-zero fails the whole build outright — no silently-broken output, matches how most pre/post-script toolchains already behave.

**A tool's process also gets two environment variables, `CANARY_ROUTE_PATH` and `CANARY_MANIFEST_PATH` (added 2026-08-20)** — enabling a class of tool that couldn't exist before: mass, programmatic modification across many pages by consulting the nav tree (e.g. "add a note to every navigable page under `games/`"), rather than a tool only ever being able to see its own page's markdown in isolation. Delivered as env vars, not CLI arguments, specifically to avoid reopening `ShellInvocation`'s `cmd.exe`-quoting minefield (see below) with a second argument to get right — env vars are read the same trivial way from `.sh`/`.ps1`/`.cmd` alike (`$CANARY_ROUTE_PATH` / `$env:CANARY_ROUTE_PATH` / `%CANARY_ROUTE_PATH%`). `CANARY_ROUTE_PATH` uses the bare nav-tree convention (`""` for the site root, e.g. `"games/tesselate"` for a nested page — see `Canary.Core.Manifest.ManifestBuilder`'s `NavItem.Path`), not `ContentScanner`'s URL-style `RoutePath` (`"/"` for root) — the two are already identical strings for every non-root route, so the bare convention was picked because it's what directly matches `manifest.json`'s own `"path"` fields with zero translation. `CANARY_MANIFEST_PATH` is the absolute path to the site's already-written `manifest.json` (`ManifestBuilder.BuildAndWrite` always runs before any tool does, so it's guaranteed current) — passed as a path, not inlined JSON, so a tool reads it itself (`jq`, `ConvertFrom-Json`, ...) rather than Canary re-serializing it into an env var. `Canary.Core.Toolchain.ToolchainContext` bundles the three same-typed strings (`SiteRoot`/`RoutePath`/`ManifestPath`) `ToolchainRunner.Run`/`Execute` need into one record, rather than stacking same-typed bare parameters that are easy to transpose by accident at a call site.

**Deliberately deferred, not part of this round** (same "revisit only if a real need shows up" reasoning as the plugin system):
- Whole-build pre/post tools (e.g. running a site's own asset build before `canary build` starts) — no concrete use case yet, unlike the per-page content case above.
- A "disable an inherited tool for this subtree" escape hatch — moot without cascading in the first place; nothing to disable if nothing is inherited.

**Implementation, and the checksum-gating fix that came with it (2026-08-18).** New `Canary.Core.Toolchain` namespace (named `Canary.Core.Hooks` until the 2026-08-21 rename to this section's current terminology), kept deliberately separate from `Canary.Core.Manifest` per the design above: `ToolchainOverride` (the `.toolchain.json` data model), `ToolchainOverrideFile` (load + auto-create, mirroring `.nav.json`'s pattern but recursing to every depth), `ToolchainRunner` (chains a page's applicable tools via `System.Diagnostics.Process`, piping stdin/stdout; also exposed a separate cheap `ChecksumSeed` that never actually executed anything). `SiteBuilder` wires it in: `.toolchain.json` auto-creation runs once per build off the same route list `ContentScanner` already computed (not a second filesystem walk); each route resolves its directory's applicable tools and only actually runs them on a cache miss.

That last point is the other half of this work — **the checksum-gating known bug (widgets *and* the toolchain) got fixed in the same pass**, as planned. `PageBuilder.BuildPage` gained an `extraChecksumSeed` parameter (folded into the hash alongside the markdown source) and a `transformSource` callback (applied only on a cache miss — running the toolchain is potentially expensive, so unconditionally running it just to decide whether to skip it would defeat the entire point of the gate). `SiteBuilder` computes one combined hash of every discovered widget file's content, once per build (same site-wide-not-per-page-usage tradeoff already made for `{{widgetScripts}}`), plus each route's tool-specific seed (tool names + their registered commands + the referenced script's own content when the command resolves to a real file under the site root). The embedded HTML comment was renamed `source-checksum` → `content-checksum` to honestly reflect that it no longer covers just the markdown source (`PageBuilder`'s regex, and the "Incremental builds" section below, both updated to match).

Three real bugs found via actual testing, not by inspection, same standard as everywhere else in this project:
1. **`cmd.exe`'s command-line quoting is two bugs deep.** A tool command shaped exactly like the config example (`"tools/breadcrumb.sh"`) failed outright the first time it was actually run: `cmd /c tools/breadcrumb.sh` gets misparsed because cmd's switch scanner keeps looking for more `/x`-shaped switches anywhere after `/c`, so the forward slash inside the path reads as a second switch. The obvious fix — wrapping the whole command in quotes — *also* failed, because cmd only preserves quotes under specific conditions (see `cmd /?`), one of which requires whitespace *inside* the quoted string; a bare path has none, so cmd silently strips the quotes and the bug comes right back. Fixed by prefixing with `call ` (`/c "call tools/breadcrumb.sh"`), which reliably satisfies that whitespace condition regardless of what the command actually is — verified empirically against real `cmd.exe` invocations (including that exit codes still propagate) before landing it, not just reasoned about.
2. A test-fixture gap, not a product bug, but worth noting since it briefly looked like the checksum fix itself was broken: `SiteBuilderToolchainTests`'s (then `SiteBuilderHooksTests`) minimal `shell.html` fixture (copied from an existing test file) didn't include a `{{checksum}}` placeholder, so the checksum comment was never embedded in output at all — every build looked like a cache miss regardless of what changed. Confirmed as a test-only issue by reproducing the exact same symptom with the real CLI against a similarly minimal `shell.html`.
3. **A real race in `ToolchainRunner.Execute`, surfaced later by an intermittently-failing test.** Writing to `process.StandardInput` after the child process has already exited (e.g. a tool command like `exit /b 1` that exits immediately without ever reading stdin, or any fast-failing/input-ignoring tool) throws an `IOException` (broken pipe) that masked the real, intended error — a clean "tool exited non-zero" message. Fixed by wrapping the stdin write in a `try`/`catch (IOException)`: a broken pipe there is an expected, benign condition, not the actual failure signal, which is the exit code checked immediately after. Verified by running the affected test 5 times in a row after the fix (it's a timing-dependent race, so a single green run doesn't prove much on its own).

## Project configuration file (`canary.json`)

Lives at a site's root, named `canary.json` (renamed 2026-08-21 from the more generic `config.json` — a directory listing should signal "this is a Canary site" the same way `package.json`/`tsconfig.json` do for their own tools). Format is JSON (matches the existing `manifest.json` convention, zero new parsing dependency). v1 shape — one config per environment (no dev/prod split), nav/routes always derived from `content.root` + generated manifest (never redeclared in config), single flat content root:

```json
{
  "site": { "name": "...", "baseUrl": "https://..." },
  "content": { "root": "content/" },
  "output": { "dir": "docs" },
  "renderMode": "hybrid",
  "nav": { "depth": 1 },
  "serve": { "port": 6913 },
  "theme": { "shell": "templates/shell.html", "base": "css/framework.css", "theme": "css/theme.css" },
  "widgets": { "copyDefaultsOnInit": true, "preferBuiltIn": false },
  "tools": { "breadcrumb": "tools/breadcrumb.sh" }
}
```

**`serve.port` (default `6913`, added 2026-08-21; randomized-per-project generation added same day)** — the port `canary serve` binds to when `--port` isn't passed on the command line (`--port` still wins over this when given). `6913` is `CanaryConfig`'s own static fallback for a hand-written `canary.json` that omits `serve` entirely, but `canary init` never actually writes that fixed value: it generates a fresh random port in `[6500, 7000)` on every run (via `Program.GenerateRandomServePort`) instead, whether interactive (shown as the prompt's default, overridable) or `--config` mode (silent, same treatment as theme paths and the tools registry — never copied from the source). Two sibling projects scaffolded from the same template minutes apart still get different default ports, so running `canary serve` on both at once doesn't collide by default. The `[6500, 7000)` range (and the `6913` static fallback, itself inside it) was picked to avoid the well-known local-dev defaults every other tool on a machine is already fighting over (`3000`/`3001` Node/React, `4200` Angular, `5000`/`5001` Flask/Kestrel, `5173` Vite, `8000` Django, `8080`/`8081`, `8888` Jupyter, `9000` PHP-FPM/SonarQube) — the user's own instinct, refined from "just pick one uncommon fixed default" to "generate one per project" once they clarified the actual goal was avoiding *cross-project* collisions, not just avoiding well-known ones.

No structured `deploy` block — see **Core built-in functionality** above for why: `output.dir` is the entire deploy story for git-served hosts, and for anything else there's `publish` (a bare string, not a target abstraction with a target-specific credential/config shape — see **Publishing**). No FTP/SFTP-target-specific config field was ever added, deliberately: a site author's own `publish` command handles its own credentials however it wants (env var, OS credential store, ...), the same way it always would have outside Canary.

**`nav.depth` (implemented 2026-08-18) — how many directory levels deep the generated nav *menu* recurses**, default `1`. This was a real gap, not a deliberate v1 scope choice: `ManifestBuilder`'s nav-tree builder had been hardcoded to one level ever since it was ported from consoland's own `build-manifest.cs` — a fine default for consoland's genuinely flat site, but a site-specific assumption that had just been sitting there unexamined, not a universal rule. It broke down the moment a site needed real nested structure (the motivating case: Canary's own future docs site, e.g. `docs/guides/widgets.md` — a page two directories deep that the nav tree would otherwise never surface at all, even though `ContentScanner` already builds and serves it as a real page regardless of nav depth). `<= 0` means unlimited depth.

Implementation: `ManifestBuilder.BuildDirectoryNavItem` now recurses into a directory's own subdirectories exactly the same way it already handled the directory itself — a nested directory becomes a nav item with its own landing page/children, sorted alongside its sibling *files* in one dropdown (priority-then-title, same rule the top level already used, now applied uniformly at every level). `.nav.json` auto-creation, which used to be implicitly capped at top-level directories for the same "nav tree only goes one level" reason, now reaches exactly as deep as the nav tree itself does — no second, separately-tracked depth limit to keep in sync.

The client side needed real work too, not just a pass-through: `runtime/ts/nav.ts`'s renderer used to flatten every dropdown child into a plain `<a>`, with no recursion at all — a deeper `NavItem.Children` in the JSON manifest would have been silently truncated by the browser even with the C# side fully fixed. Rewritten so a child with its own children renders as a nested flyout submenu (`.nav-subitem`, hover/focus-gated independently of its parent dropdown) instead of losing its grandchildren; `updateActiveNav` rewritten to walk up the DOM from whatever depth actually matched, marking every ancestor level active, rather than only ever checking one level. A depth-1 site's markup and behavior are byte-for-byte unchanged by any of this — the new code paths only ever activate once a `NavItem` genuinely has grandchildren, which never happens at `nav.depth: 1`.

**The submenu's "further" chevron took three attempts to actually fix, worth recording because the first two both looked correct and weren't** — a real lesson in verifying against the DOM, not a screenshot. User review caught it first: the chevron indicating a row expands further was rendering flush against the label text. Attempt 1 assumed `justify-content: space-between` just needed slack width it didn't have, and swapped to a fixed `gap` — looked unchanged when re-checked, still touching. Attempt 2 theorized a `::after` pseudo-element merges into the same anonymous flex item as its adjacent text (so `gap` would have nothing to apply between them) and switched the chevron to a real sibling `<span>` — *still* touching, confirmed via a zoomed screenshot in a brand-new tab (ruling out cache). Only inspecting `getComputedStyle` directly found the actual bug: `.nav-dropdown-label`'s own `display: flex` was never winning at all — the pre-existing `.nav-dropdown a { display: block; ... }` rule has higher CSS specificity (`0,1,1` vs. `.nav-dropdown-label`'s `0,1,0`) and silently overrode it every time, so the element was never a flex container in the first place and `gap` had nothing to act on regardless of which fix was tried. Fixed by qualifying the selector to `.nav-dropdown .nav-dropdown-label` (specificity `0,2,0`, safely above `.nav-dropdown a`). Verified this time by measuring the actual rendered gap between the two spans' `getBoundingClientRect()`s (8px, exactly `0.5rem`) rather than trusting another screenshot.

Verified: 136/136 tests (7 new `ManifestBuilderTests` covering default-depth-omits, depth-2, unlimited depth, mixed file/directory sibling ordering, and `.nav.json` backfill at depth), plus a real three-level-deep dogfood extension of `workspace/` (a new "Background" section — `background/history/copyright-dispute.md`, `background/production/original-cast.md` — kept in permanently, same as every other dogfooded feature), driven in an actual browser: the nested flyout submenu opens correctly on hover, all three ancestor levels (top-level item, nested subitem, leaf link) highlight active together when viewing the deepest page, in both `hybrid` (fragment-fetch) and `static` (real full-page loads) modes, zero console errors. Also caught and fixed, incidentally: `workspace/css/framework.css` had drifted out of sync with `templates/default/css/framework.css` since the widget-CSS-extraction fix earlier the same day — a stale copy nobody had re-synced. Re-copied.

**`widgets` schema landed 2026-08-17, `copyDefaultsOnInit` wired up 2026-08-21 (see Scaffolding); `preferBuiltIn` still schema-only** (`Canary.Core.Config.WidgetsConfig` — parses, validates, has sensible defaults):
- `copyDefaultsOnInit` (default `true`) — on `canary init`, copy the built-in widgets into the new project's own `widgets/` folder as an editable starting point, "eject"-style (like Create React App's `eject`), rather than leaving them invisible inside Canary's own install. Since site-authored widgets already win on a name collision, this makes the copies active immediately. **Resolved 2026-08-21: `canary init` always overwrites these two files on every run**, not just on a truly fresh project — user's call, simpler than "copy once," and `preferBuiltIn` already exists as the escape hatch for anyone who wants their local edits to stop tracking Canary's built-ins.
- `preferBuiltIn` (default `false`) — single site-wide switch (not per-widget, confirmed with the user), the escape hatch for the above: a project with its own copies is normally frozen at whatever Canary shipped at init time; flipping this ignores the project's local `widgets/downloads.html`/`slideshow.html` even if present, and always uses Canary's current built-in versions instead — without deleting local files. `canary init` prompts for/accepts this value and writes it to `canary.json`; still needs a precedence-flip added to `Widgets.WidgetDiscovery` itself (today: site-authored unconditionally wins regardless of this setting) — separate, not-yet-done work.

## CLI surface

- `canary init [path] [--config <path>] [--force]` — scaffold a new site into `path` (default `.`). Two modes: pass an existing `canary.json` via `--config` to pull core values from directly (site name, base URL, render mode, content root, output dir, nav depth, widgets flags — theme paths, tools, and the serve port are always the fresh scaffold's own, never copied from the source), or omit `--config` and get prompted interactively for the same fields one at a time (serve port included, each showing its default — a freshly generated random one for the port). Refuses to touch a target directory that already has a `canary.json` unless `--force` is passed — see **Scaffolding** below for the full design (implemented 2026-08-21).
- `canary build` — full build: manifest generation, chrome re-stamp (always), content render (every page, every time — see **Incremental builds**, below, for why and how it still keeps `output.dir` diffs clean), sitemap/robots generation, all written to `output.dir`. For a git-served host like GitHub Pages, this *is* the deploy step — the site owner commits/pushes `output.dir` themselves.
- `canary serve [--config <path>] [--port <n>]` — local dev server against the config, for iterating before committing/pushing. Binds to `--port` if given, otherwise `canary.json`'s `serve.port` (default `6913`). Rebuilds on file change; a plain edit to one page's markdown triggers a targeted rebuild of just that page (see **Incremental builds**), anything else falls back to a full rebuild.
- `canary publish [--config <path>]` — builds, then runs `canary.json`'s `publish` command. See **Publishing** below (implemented 2026-08-21).
- `canary docs [--force]` (implemented 2026-08-21) — no `--config`: opens Canary's own bundled docs (`docs/`, the repo root's, resolved via the same `ResolveRepoSubdir` walk-up `templates/default`/`runtime/dist` already use) in the default browser, served on a random port actually verified free (via a bind-then-release `TcpListener` probe, not just an uncommon-range guess like `canary init`'s serve-port default) in `[9000, 9999]`. See **Documentation site** below — this is the `canary docs` command that section's "deliberately deferred" note said would need to exist before shipping the docs alongside the binary was worth doing; it now does, and the docs are still resolved from the source checkout rather than copied anywhere, since that's still all a from-source run needs. **Single-instance, added same day at the user's own request**: starting it writes a lock file (pid + port, JSON) to `%APPDATA%/Canary/docs.lock.json` (`Environment.SpecialFolder.ApplicationData`, cross-platform via the .NET API rather than a hardcoded Windows path, even though it's only been run on Windows so far); a second `canary docs` while that pid is still alive just prints where the first one is and exits, rather than opening a redundant second server on a second port. `--force` kills the existing process (`Process.Kill()` + a bounded `WaitForExit`, best-effort — "try to close," per the user's own framing, not guaranteed) and starts fresh; a lock file whose pid has already died on its own (a crash, not a clean exit — the common "hung process" case `--force` exists for doesn't even need it, only a genuinely still-alive-but-stuck one does) is detected and silently cleaned up with no `--force` required. Graceful shutdown (Ctrl+C) deletes the lock itself, in a `finally` around the serve loop. `IsProcessAlive`'s pid check also confirms the process name looks like `Canary`/`dotnet` before trusting it, a cheap (not airtight) guard against a stale pid having been reused by an unrelated process since.

## Scaffolding — `canary init` (implemented 2026-08-21)

The last item from the original phase list. Wires up the CLI surface and config schema this doc already specified, plus resolves two things that were genuinely open until now:

- **Widget re-copy on re-init**: resolved to *always* overwrite `widgets/downloads.{html,js,css}`/`slideshow.{html,js,css}` on every `canary init` run (not just a fresh project) — see **Project configuration file**'s `widgets` notes above for the reasoning.
- **What happens when `canary.json` already exists in the target directory**: resolved by adding an explicit `initialized: true` marker to `canary.json` itself, written by `canary init` on success. `canary init` refuses to touch a target directory whose `canary.json` already exists at all (regardless of the flag's value — the flag only changes the wording of the refusal message: "already an initialized Canary project" vs. "a canary.json already exists here that wasn't created by canary init") unless `--force` is passed. Chosen over inferring "already a project" from the file's mere presence because it's a self-documenting marker `canary init` itself controls, rather than an implicit heuristic — the same "explicit beats implicit" preference behind the `!url` widget tag and non-cascading toolchain application elsewhere in this doc. `Canary.Core.Config.CanaryConfig.Initialized` (bool) — not validated by `ConfigLoader`, not read anywhere in the build/serve pipeline, purely `canary init`'s own bookkeeping.

**What gets scaffolded**, via the new `Canary.Core.Init.SiteInitializer` (no `Console` I/O, mirrors `SiteBuilder`/`ConfigLoader` — all prompting stays in `Program.cs`):
1. `canary.json`, hand-built as a `JsonObject` (not `JsonSerializer.Serialize(CanaryConfig)`, which would emit PascalCase keys inconsistent with every hand-authored config in the repo) — `site`/`content`/`output`/`renderMode`/`nav`/`serve` from the resolved input values, `theme` always fixed to the paths init itself scaffolds (`shell.html`/`css/framework.css`/`css/theme.css` — never copied from a `--config` source, since that source might point at theme files that don't exist in the new project), `tools` always exactly `{ "example": "dotnet run tools/example.cs" }` (registering the example tool from step 2 below, never copied from a `--config` source's own registry), `initialized: true`. `serve.port` specifically is never copied from a `--config` source either, even though it's a plain value that safely could be — see `serve.port` above for why.
2. `shell.html` + `css/framework.css`, copied from `templates/default/`; `css/theme.css`, copied from a new generic starter also added to `templates/default/` (didn't exist before — only `workspace/`'s site-specific theme did); `tools/example.cs`, a new starter **toolchain** tool also added to `templates/default/` (echoes stdin to stdout unchanged, line by line — a working, do-nothing-to-the-markdown passthrough to copy/rename/edit rather than write one from scratch, that also loads `CANARY_ROUTE_PATH`/`CANARY_MANIFEST_PATH` into local variables and writes them to stderr, purely to demonstrate they're there — stderr, not stdout, so it stays a genuine stdout no-op). All four always overwritten once execution reaches this point (fresh init or `--force`). `tools/example.cs` is registered in `canary.json` (step 1) but not applied anywhere — no `.toolchain.json` gets written referencing it, matching the "registration and application are separate, application is never automatic" design from **Content toolchain** above; a site author opts in by adding `"example"` to a directory's own `.toolchain.json`.
3. `<content.root>/index.md` — created **only if it doesn't already exist**, never overwritten even with `--force`, since it's real content, not framework scaffold (unlike the widgets/theme/tool files above, which are meant to track Canary's own defaults).
4. `widgets/{downloads,slideshow}.{html,js,css}`, copied from the resolved runtime dist dir, when `widgets.copyDefaultsOnInit` is true — always overwritten (see above).

**CLI**: `canary init [path] [--config <path>] [--force]`. No `--config`: prompts interactively (`Console.ReadLine`, one field at a time, showing each default) for site name, base URL, render mode, content root, output dir, nav depth, serve port (default shown is a freshly generated random one, not a fixed constant — see `serve.port` above), and both widgets flags. A required field (site name, base URL) with no default treats EOF on stdin (a closed pipe, no TTY, input that ran out) as a fatal error rather than looping forever re-asking — found by actually testing a piped/non-interactive run, not by inspection. `--config <path>`: loads that file via the existing `ConfigLoader.Load` and pulls only the core values listed above from it — never its theme paths, tools registry, or serve port, for the reason in step 1 (and `serve.port`'s own note above).

## Publishing — `canary publish` (implemented 2026-08-21)

The user's own framing: "not necessarily [git add/commit/push], because people will host sites in different ways so we want a simple, run this, for canary publish." `canary.json`'s top-level `publish` field is a single arbitrary shell command string — not a deploy-target abstraction, not a git-specific or FTP-specific mechanism, just "run this." Same anti-abstraction philosophy as a toolchain tool: Canary doesn't know or want to know how a site is actually hosted.

```json
{ "publish": "git add docs && git commit -m \"Publish\" && git push" }
```

**`canary publish` always builds first**, then runs the configured command — publishing stale output would be worse than refusing to publish at all. If `publish` isn't set, it fails clearly (`No publish command configured...`) rather than silently doing nothing.

**One environment variable**: `CANARY_OUTPUT_DIR`, the absolute path to `output.dir`, so a publish command can reference the real build output location without hardcoding/duplicating the directory name that's already declared elsewhere in `canary.json`. No per-page context (`CANARY_ROUTE_PATH`/`CANARY_MANIFEST_PATH`) — publishing is a whole-site action, not a per-page one, so those don't apply here.

**Live output, deliberately not buffered.** `Canary.Core.Publish.PublishRunner` redirects the child's stdout/stderr but forwards each line to `Console.Out`/`Console.Error` as it arrives (`OutputDataReceived`/`ErrorDataReceived` + `Begin...ReadLine`), rather than either (a) capturing it all and dumping it after the fact like `ToolchainRunner` does (wrong here — a publish command's whole point, e.g. `git push`'s progress output, is watching it happen), or (b) simply *not* redirecting and letting the child inherit the console's handles directly (the first thing tried — **found via a real test failure** that this fails outright, exit code 1, in a non-interactive host with no attached console to inherit; streaming redirected output turned out to be the more broadly correct choice, not just an equivalent one).

**Execution reuses `ToolchainRunner`'s hard-won `cmd.exe` quoting fix, extracted into `Canary.Core.Shell.ShellCommand.Resolve`** (moved out of `ToolchainRunner`, which now calls the shared version) rather than re-deriving or duplicating it — a toolchain tool and a publish command are both "run this arbitrary string as a shell command," so there's no reason to solve the same quoting problem twice.

**A second, previously-undiscovered `cmd.exe`/Windows landmine turned up building this — found by a real command that should have worked failing anyway, same standard as everywhere else.** A bare filename with no path separator (e.g. `"publish": "publish.cmd"`, the script sitting directly in the site root) silently fails to resolve under `call`, but only on a machine with the `NoDefaultCurrentDirectoryInExePath` security hardening setting enabled — a real, sometimes IT-policy-enforced Windows setting, not an artifact of any particular dev environment. That setting disables implicit current-directory search for a bare name; a path *with* a separator (`./publish.cmd`, `tools/publish.cmd`) is unaffected because it bypasses that search algorithm entirely rather than going through it. **Deliberately not "fixed" in code**: `ShellCommand.Resolve` has no way to tell "bare name meaning a local file" (needs a path prefix) apart from "bare name meaning a PATH-resolved executable" (a prefix would break it — `dotnet`, `git`, `powershell` are exactly this shape) without checking the filesystem, and it isn't even given a working directory to check against. Documented instead, both in `ShellCommand`'s own comment and here: **always write a local script command with an explicit path** (`tools/foo.cmd`, `./foo.cmd`), never a bare `foo.cmd`. Every command Canary itself ships already follows this (`dotnet run tools/example.cs`, `tools/breadcrumb.sh`).

Verified: `dotnet test` (148/148, including new `PublishRunnerTests` — success/failure/`CANARY_OUTPUT_DIR`/working-directory coverage, fixture scripts deliberately placed under a `publish/` subdirectory rather than as bare filenames, both to avoid the landmine above and to prove the guidance actually works), plus live end-to-end: scaffolded a fresh project, set `publish` to an `echo %CANARY_OUTPUT_DIR%`-style command, ran `canary publish` and confirmed it built first, streamed the command's own output live, resolved `CANARY_OUTPUT_DIR` to the real absolute `docs/` path, and exited 0; running it again against `workspace/` (which has no `publish` configured) correctly failed with the clear "no publish command configured" message instead of doing nothing silently.

## Incremental builds

**Replaced checksum-gating entirely (2026-08-20) — see the dated Resolved entry below for the full reasoning and implementation.** The short version: checksum-gating (an embedded `<!-- content-checksum: sha256:... -->` comment per page, compared against a freshly computed hash to decide whether to skip re-rendering) needed repeated bug-fix passes over its life (missed widget files, missed tool scripts, a `cmd.exe` quoting bug, a `ToolchainRunner` race, a test-fixture gap) and was cut in favor of two much smaller mechanisms that don't need any invalidation-tracking at all:

- Chrome (header/nav/footer skeleton + script/style tags) is **unconditionally re-stamped every build**, same as always — it's cheap and always current from one source template, so there's no "did it change" case to special-case.
- **Every page is always fully re-rendered** (markdown + the toolchain's applicable tools run unconditionally, every build) — there is no cache to hit or miss. What's still conditional is the disk **write**: since rendering is deterministic, `PageBuilder.BuildPage` compares the freshly-rendered HTML against whatever's already on disk at that path and only calls `File.WriteAllText` when it actually differs. That keeps a committed `output.dir`'s git diffs small and meaningful by direct comparison against reality, rather than by tracking every input that could make a cached result stale (the exact bug class that kept recurring).
- **`canary serve` gets its speed back a different way: targeted single-route rebuilds.** `Canary.Core.Serve.SiteWatcher` now accumulates which file(s) changed during its debounce window and passes that set through to `SiteBuilder.Build`'s `changedPaths` parameter. If every changed path is a plain edit to an existing route's own source file, only that route gets rendered; anything else (a page created/deleted/renamed, or a non-content file like a widget/tool-script/theme/`canary.json` edit) falls back to rendering every route, since those could affect more than one page and Canary isn't going to guess. The site-wide bookkeeping (manifest, `.toolchain.json` auto-creation, sitemap/robots, asset copies) always runs in full regardless — it's cheap, and skipping it would risk the nav tree/sitemap going stale.
- `BuildSummary`'s `PagesWritten`/`PagesUnchanged` counters (renamed from `PagesRendered`/`PagesReusedUnchanged`) reflect this honestly: "written" means the file on disk actually changed, "unchanged" means it was computed fresh but happened to be identical — a distinction that, by construction, can never disagree with what `git status` would show.

## Documentation site (`docsite/`, implemented 2026-08-21)

A second dogfood site, `docsite/` — this time not a fake example but Canary's own real user-facing documentation, built by the exact same `canary build` a consumer would run. Home page, Getting Started (CLI walkthrough + what `init` scaffolds), Guide (render modes, widgets, toolchain, publishing, incremental builds, the "why" pitch), and Reference (`canary.json`, CLI, FAQ) — 14 routes total. `renderMode: hybrid`, `nav.depth: 1` (no nested subdirectories needed at that depth for this content).

**`output.dir` is `../docs`, unlike `workspace/`'s output**: this site's build output is meant to actually reach GitHub (viewable in-browser, GitHub Pages-servable from `/docs` on `main`), not stay disposable like `workspace/docs`'s — see the correction above. That required carving `.gitignore`'s blanket `docs/` rule (`docs/` / `!/docs/`) so the *repo root's* `docs/` is tracked while any other site's `docs/` output (`workspace/`'s included) stays ignored by default.

**A real markdown-renderer constraint surfaced writing this content, actually fixed, not just worked around**: `MarkdownRenderer.FenceRegex` (`^```(.*)$`) has no concept of nesting or backtick-count escaping (unlike CommonMark's "more backticks than the content contains" convention) — a widget name as a fence's info string (`downloads`, `slideshow`) always dispatches to that widget, with no way to show the literal fence syntax as inline documentation text. First pass worked around it by describing each widget's YAML fields in prose/lists instead of a literal example (user's own reaction: build a widget for this instead of just describing around it) — **fixed properly by adding a third built-in widget, `code`** (`runtime/widgets/code.{html,css}`), which renders a `lines` list (each entry a one-field `text` map — YAML has no multi-line block-scalar support here, so one list entry per source line is the only way to get free-form multi-line text through at all) back out as an escaped, verbatim `<pre><code>` block. Wrapping an example one line at a time inside `code`'s fence sidesteps the no-escape problem entirely: the *outer* fence's info string is `code`, so it renders instead of running, and the inner text — including a literal `` ``` `` on its own line — is just data, never re-scanned for fence boundaries. `guide/widgets.md` now shows real, correct fence examples for `downloads` and `slideshow` this way instead of prose-only field lists. Also discovered along the way: `CodeSpanRegex` (markdown's inline code, a separate renderer from the widget templater) is a single-backtick-pair match with no CommonMark-style double-backtick escape for a literal backtick inside inline code — noted, not worked around, same reason.

**A second, unrelated bug found building the `code` widget's own example**: `YamlParser.ParseScalarText` strips a scalar's matching outer quote pair but never unescapes a backslash inside one — a line written as `"...\"...\""` (trying to represent a literal double quote via backslash-escaping, like most other languages' string syntax) comes out with the literal backslash still in it, not the quote intended. Not a bug in the sense of violating this YAML subset's own documented rules (it never claimed to support backslash escapes), but a real footgun for anyone reaching for the "obvious" escape from muscle memory — found by actually rendering the widget's own clipboard example and reading the malformed output (`\&quot;My File\&quot;`), not by inspection. Fixed by using single quotes as the line's own delimiter instead whenever it contains a literal double quote (`'  - label: "My File"'`) — no parser change, just the correct way to write it given the parser's real, intentional constraints. Documented directly in `code.html`'s own doc comment and in `guide/widgets.md`, not just here, so the next author hits the explanation before the bug.

## Resolved (for reference — no longer open)

- **`hybrid` mode's router switched from hash-based to real-path (History API) navigation (2026-08-20).** Prompted by re-examining the "stale hash + real path mismatch" known bug: the hash was only ever structurally necessary for a pure client-rendered SPA with no real per-route files (GitHub Pages can't rewrite server-side — see **Origin**), and `hybrid` never had that constraint, since every route already has a real prerendered file at its real path. The hash in `hybrid` was vestigial, carried over from when the router was ported from consoland's original pure-SPA design — not something `hybrid` actually needed. Removing it eliminates the bug class by construction (the address bar always shows the real path, so there's no second "hash says X, server served Y" state to go stale) rather than patching around it, and drops the "f-ed" `/games/#/games/tesselate`-shaped URLs the user flagged as ugly in their own right.
  - `router.ts` rewritten around `pushState`/`popstate` instead of `hashchange`: it now delegates a `click` listener on `document`, intercepts a plain left-click on a same-origin `<a href>` (skipping modified clicks, new-tab/download links, cross-origin links, and same-page `#fragment` anchors, which stay native), `preventDefault`s the browser's own navigation, and does `pushState` + dispatch instead. Back/forward is `popstate`. This also means in-content markdown links now get the same instant SPA-style swap nav links always had — previously only hash-linked nav triggered the fragment-fetch, while in-content links (already real hrefs) fell through to a full reload; uniform interception was simpler to write than special-casing "only intercept nav's own links," and removes that inconsistency as a side effect.
  - `hybrid-router.ts` simplified: `route.path` from the new router is already the real pathname (stripped of slashes, `""` for root) — no more `contentFileFor`/hash-parsing translation layer, and no more separately tracked `currentPath` mutable state or `currentPathFromLocation` cold-load workaround (that workaround existed specifically to patch over hash-vs-path disagreement, which can't happen anymore).
  - `nav.ts` simplified alongside it: since both `hybrid` and `static` now want the exact same real-path href shape (`hrefFor`) and the exact same "read `window.location.pathname`" current-route logic, the per-mode `hrefFor`/`getCurrentPath` parameters `loadNav`/`updateActiveNav` used to take were no longer serving two different values — inlined as module-level functions instead of a now-pointless injection point. `static-nav.ts` shrank to a single `loadNav()` call.
  - Verified: `npm run build` (tsc clean), `dotnet test` (137/137, including a comment-only update to `ManifestBuilderTests`), and a real rebuild + browser test of `workspace/` in both modes — confirmed no console errors, real (non-hash) URLs in the address bar through nav clicks and nested-flyout clicks, instant content swap with correct nav highlighting (including at `nav.depth: 2`), correct `popstate` behavior on browser Back, and — the actual bug scenario — a cold load/hard-refresh directly on a deep bookmarked URL (`/characters/frederic/`) now shows the right content *and* the right nav highlighting immediately, with no possible hash to disagree with the served path.
  - `Canary.Core.Manifest.ManifestBuilder`'s and its test's comments (which referenced the old `href="#/${path}"` convention) updated to describe the real-path convention instead; `README.md` and `runtime/ts/package.json`'s descriptions (which called it a "hash-router") updated to match.
- **Checksum-gating replaced with write-only-if-different + targeted single-route rebuilds; the toolchain gains `CANARY_ROUTE_PATH`/`CANARY_MANIFEST_PATH` (2026-08-20).** The user's call: checksum-gating's reliability cost (see the repeated bug-fix history logged elsewhere in this doc) wasn't worth what it bought, and what it bought turned out to be two separable things — see **Incremental builds** above for the full design (write-only-if-different for clean `output.dir` diffs; `SiteWatcher`-driven targeted rebuilds for `canary serve` speed). Landed together with a second, related change: a toolchain tool can now read `CANARY_ROUTE_PATH`/`CANARY_MANIFEST_PATH` off its process environment (see **Content toolchain**'s Execution model), enabling mass, programmatic modification across pages by consulting the nav tree — the motivating case, from the user: a tool that adds something to every navigable page under `games/`. The two land together because removing checksum-gating also resolved the one real correctness gap the route-path/manifest feature would otherwise have introduced: a tool whose output depends on the manifest (not just its own page's markdown) could have gone stale under a cache that didn't also track manifest changes — the exact "gate doesn't track everything a tool can see" bug class already hit twice (widgets, then tool scripts). With no gate at all, that problem doesn't exist.
  - `Canary.Core.Build.PageBuilder`: `ComputeChecksum`/`TryReuseExisting`/the two checksum `[GeneratedRegex]` methods/`extraChecksumSeed` all removed; `BuildPage` always renders, and only skips `File.WriteAllText` when the freshly-built HTML is byte-identical to what's already on disk. `ContentRenderOutcome` renamed `PageWriteOutcome { Written, Unchanged }`. The `{{checksum}}` shell-template placeholder is gone (no compat shim — pre-release, confirmed not needed) from both `templates/default/shell.html` and `workspace/shell.html`.
  - `Canary.Core.Build.BuildSummary`: `PagesRendered`/`PagesReusedUnchanged` renamed `PagesWritten`/`PagesUnchanged` to describe what's actually true now; `TotalRoutes` stays the full site's route count regardless of whether a build was targeted.
  - `Canary.Core.Serve.SiteWatcher`: now accumulates changed paths from `Changed` events during its debounce window and passes them through (`Action<IReadOnlySet<string>?>` instead of a bare `Action`); a `Created`/`Deleted`/`Renamed` event anywhere in the same window forces `null` (full rebuild) instead, rather than trying to reason about what a structural change actually affects. `SiteBuilder.Build` gained a `changedPaths` parameter: `null` renders every route (unchanged default behavior); a set where every path matches an existing route's own `SourcePath` renders only those routes; a set containing anything else (a widget/tool-script/theme/`canary.json` edit) falls back to rendering everything.
  - `Canary.Core.Toolchain.ToolchainRunner` (then `Canary.Core.Hooks.HookRunner`, before the 2026-08-21 rename): `ChecksumSeed` deleted entirely (nothing computes a seed anymore). `Run`/`Execute` take a new `ToolchainContext(SiteRoot, RoutePath, ManifestPath)` record instead of a bare `siteRoot` string, to avoid a same-typed-parameter transposition footgun now that there are three route/path-shaped strings in play; `Execute` sets `CANARY_ROUTE_PATH`/`CANARY_MANIFEST_PATH` on the child process's environment from it.
  - Verified: `dotnet test` (138/138, replacing/extending the old checksum-focused tests — including a new build-twice-in-a-row idempotency test to cover what the deleted `Build_NothingChanged_StillReusesCachedPage` used to incidentally guard, and new `SiteWatcherTests`/`SiteBuilderToolchainTests`/`ToolchainRunnerTests` coverage for targeted rebuilds and the new env vars), plus live verification against `workspace/`: a bare rebuild with nothing changed shows `written=0, unchanged=11`; editing one page's markdown while `canary serve` was running triggered a `[rebuild]` that processed exactly that one route (`written=1, unchanged=0`, not 11); editing a theme CSS file correctly fell back to a full rebuild (`written=0, unchanged=11`, all 11 routes processed); and a temporary debug tool confirmed a nested page (`characters/frederic`) receives `CANARY_ROUTE_PATH=characters/frederic` and a `CANARY_MANIFEST_PATH` pointing at a real, current `manifest.json` containing that exact route.

- **Does `static` mode ship zero client JS?** → no, nav (`loadNav()`) and widgets still run as JS in every mode; what's mode-specific is content routing/rendering, not "JS or no JS."
- **Config schema for v1** → settled shape above; single config (no env split), nav/routes always derived from content + manifest (never redeclared), single flat content root.
- **Runtime bundle: one-size-fits-all vs. per-mode-tailored** → tailored per `renderMode`; markdown renderer only shipped in `spa` bundles, back when `spa` existed (see below — now moot, there's no client-side markdown renderer left at all).
- **`spa` mode: directory-index landing pages 404'd client-side** → found and fixed 2026-08-17 while dogfooding `spa`/`static` end-to-end in a real browser against `workspace/` (`spa-router.ts`'s `contentFileFor()` only special-cased the root route, so a subdirectory's landing page like `/characters` fetched `content/characters.md` instead of `content/characters/index.md` and 404'd; fixed with a leaf-then-directory-index fallback fetch). **Superseded the next day** — `spa` mode itself was removed entirely (see below), taking `spa-router.ts` and this fix with it. Kept here for history, same as the widget-system round-1 entry above.
- **`spa` mode removed entirely (decided and done, 2026-08-18).** Surfaced while designing the **Content toolchain**: a toolchain tool is an arbitrary external command with no browser equivalent, so it can only ever run at build time — which meant `spa` mode would have had to prerender to get the toolchain working at all, at which point it was no longer meaningfully different from `hybrid` in *how content gets built*, only in navigation policy. Once that justification was gone, the user's call was direct: "Its time for SPA to die." Removed: the `RenderMode.Spa` enum value, `SiteBuilder.BuildSpa`, `RuntimeAssetManifest`'s spa entry, `runtime/ts/spa-router.ts`, `runtime/ts/markdown.ts` (the client-side markdown renderer — `spa` was the only mode that ever ran it in the browser, so nothing needs it now), and the spa-specific test cases in `ConfigLoaderTests`/`SiteBuilderSeoTests`. `SiteBuilder.CopyContentAssets` and sitemap/robots generation both simplified since there's no longer a mode that needs different treatment (markdown is now unconditionally excluded from the content copy; SEO files are now unconditionally written). This also retired two other standing gaps for free: the "Still open" client-side widget-rendering gap from **Widget system** (moot — widgets only ever render at build time now, in every mode) and the "does the `!url` tag work client-side" question (same reason). Verified: full rebuild + `dotnet build`/`dotnet test` (101/101 passing, down from 103 — the two spa-only tests were removed, not broken) + `npm run build` (TS compiles clean without the deleted files) + a full rebuild of the `workspace/` dogfood site in `hybrid` mode, all green. `spa`'s old hash-only-navigation UX is still recoverable later as a `hybrid` config flag if a real need shows up — see **Open questions**.
- **Checksum-gating didn't track widget files (and would have missed toolchain tools too)** → fixed 2026-08-18, alongside implementing the **Content toolchain** as planned (fix both gaps together in one pass, not twice). Full details, including the two real bugs found while testing the fix (a `cmd.exe` quoting issue and a test-fixture gap), are in that section above.
