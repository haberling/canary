# Canary — Website Framework

## What Canary is

Canary is a standalone C# website framework, distributed as a native-feeling CLI tool (`canary`/`canary.exe`). A "Canary site" is a directory containing a JSON project configuration file plus content (markdown) and theme assets; `canary build`/`canary serve` operate on that directory the same way for any site that adopts it — consoland included, eventually, but consoland is now a *consumer* of Canary, not the thing Canary is extracted from and tied to.

This supersedes the original framing of "split the framework pieces out of consolandWebsite." That extraction is still where the initial code comes from (see **Origin**, below), but the target is a general-purpose tool, not a one-off migration.

## Origin (institutional memory, not the current goal)

Canary began as a plan to split consolandWebsite's hand-rolled TypeScript runtime (hash router + markdown renderer + nav-from-manifest) and C# build/deploy tooling out from that site's actual content and branding — motivated by wanting the markdown-wiki site to be crawlable without losing its "no framework" hand-built character.

**Why hash routing existed in consoland in the first place**, worth carrying forward: GitHub Pages is pure static file serving with no server-side rewrites available (short of the "404.html redirect" trick). Hash routing needs zero server config — any request loads `index.html`, and the fragment after `#` is never even sent to the server, so client-side JS alone decides what renders. That's still a mode Canary needs to support well; it's just no longer the *only* mode.

## Distribution & consumption model

Canary should feel like a native CLI tool to use — `canary build`, `canary serve`, `canary.exe build` on Windows — not something invoked through `dotnet tool run` ceremony. Long-term intended distribution channel is **winget**, not a NuGet/`dotnet tool install` package; calling `dotnet tool run` for every invocation was explicitly rejected as unnatural. That preference should inform build/publish choices later (e.g. self-contained or Native AOT single-file publish, so end users don't need the .NET SDK/runtime preinstalled just to run it) — but that's a later-phase concern, not something to solve now.

For now, **local/source-only**: build and run Canary from source while it's this early. No public package (winget or otherwise) published yet — revisit once the CLI surface has stabilized through the phases below.

## Architecture: two layers

1. **C# core (the CLI/build engine)** — config loading, manifest generation, prerendering, incremental builds, output writing, sitemap/robots generation. This is Canary's actual product.
2. **Vendored client runtime (TypeScript, compiled to JS)** — the hash router, markdown renderer, and content widgets (download links, slideshow) that run in the visitor's browser. This still needs a TS toolchain to *develop*, but is pre-compiled and embedded into the Canary package at release time — a site author consuming Canary never runs `npm`/`node` themselves.

### Client runtime packaging

- TS source lives in Canary's own repo (e.g. `runtime/ts/`) and is compiled to JS via the existing npm-based toolchain, but only as part of *Canary's own* release/build process.
- The compiled output gets embedded into the Canary package (as embedded resources in the C# project, or similar) and written out to each site's build directory by `canary build`.
- Net effect: **zero Node dependency for anyone consuming Canary**, Node only matters if you're developing Canary itself.

## Render modes (config-selectable, not one-size-fits-all)

Original consoland decision was hybrid-only: prerender to real static paths *and* keep the hash-router SPA layer for in-app nav. Generalizing this for arbitrary sites, `renderMode` is a config field with two values. Both modes still run JS for nav population (`loadNav()` reading `manifest.json`, same as today) and for widgets (slideshow, downloads) — "how much JS runs" isn't what distinguishes them. What actually differs is **how in-app navigation happens** — both modes are fully prerendered; markdown→HTML always happens at build time, the browser never sees markdown source in either one:

- **`hybrid`** (what consoland needs) — a real prerendered HTML file exists per route, so cold loads (crawlers, direct links, social-preview scrapers) get real content immediately. For in-app navigation once JS has loaded, the router intercepts the click and **fetches the target route's own prerendered HTML file, extracts the `<main id="app">` fragment via `DOMParser`, and splices it into the DOM** — no full reload, and critically, no re-rendering. It's the same file, same bytes, whether you arrive cold or navigate in warm. Raw markdown is never shipped to or parsed by the client in this mode.
- **`static`** — same prerendered HTML files as hybrid, but no hash-router/content-swap layer at all. Every internal link is a real `<a href="/games/tesselate/">` href; every navigation is a full page load, handled by the browser/server, not JS. Nav and widgets still run as page-enhancement JS.

**A third mode, `spa`, existed from Phase 1 through 2026-08-18 and was removed.** It shipped raw markdown to the client and rendered it there via a dedicated client-side markdown renderer (`runtime/ts/markdown.ts`) and router (`spa-router.ts`) — no prerendered per-route files at all, closest to consoland's original pre-Canary behavior. It was cut once designing **Content hooks** made its remaining justification collapse: hooks can only ever run at build time (arbitrary external command, no browser equivalent), so `spa` would have had to prerender to get hooks working anyway — at which point it was no longer meaningfully different from `hybrid` in *how content gets built*, only in navigation policy. See **Resolved** for the full removal reasoning and **Open questions** for a config-flag-on-`hybrid` idea that could recover its hash-only-navigation behavior later, if a real need shows up.

## Core built-in functionality (absorbed from consoland's tools)

`tools/build-manifest.cs` and `tools/deploy.cs` are not going to survive as separate opt-in files a site has to wire up — their functionality (manifest/nav generation, incremental build) is core enough that it becomes **built into the Canary executable itself**, generalized away from consoland specifics (no hardcoded domain, no baked-in CNAME, no consoland branding assumptions).

**What "deploy" actually reduces to.** The real end goal across all render modes is a website that lives on a file server — Canary's job stops at producing correct output in a configurable output folder (`output.dir`, defaulting to `docs` for GitHub Pages' "serve from `/docs` on main" convention). For a git-based static host like GitHub Pages, that's the *entire* deploy story: `canary build` writes to `docs/`, the site owner commits and pushes it themselves — Canary shouldn't be auto-committing/pushing either. No bespoke GitHub-specific deploy step is needed.

A **remote push mechanism (FTP/SFTP)** is flagged as a real but later feature — build locally, verify the output, then send the already-built folder to a remote host, matching how a lot of flat-file/shared hosting actually works. This is genuinely a v-later item, not part of the core build/output story.

## Plugin system — cut from scope (for now)

Originally planned as build-time C# extensibility via Roslyn scripting (a site-supplied `.cs` file, run in-process, direct access to Canary's build objects). **Deliberately axed for now** — premature to design an extension mechanism before the core it would extend even exists. If a real need shows up once Phases 0–3 are built, revisit then with an actual use case driving the hook points, rather than speculating about them now. Not on the phase list below.

This has no bearing on **widgets** (client-side/browser-executed JS — download links, slideshow), which remain part of the vendored runtime regardless.

## Widget system — resolved controversy (2026-08-17, two rounds)

Widgets went through a real design fight, captured in full in `MostImportantControversy.md`. Short version: reviewing the ported `SlideshowWidgetRenderer.cs` surfaced a real bug (`RenderSlide` never called `ResolveUrl`), which turned into the real objection — hand-porting every widget to C# means two independent implementations of the same thing, which is exactly how that bug (and the earlier double-escape bug) happened.

**Round 1** (superseded, kept here for history): widgets as plain `.js` files with a `render(title, body) -> string` export, executed at build time via **Jint** (embedded JS interpreter). This fixed the "two implementations" problem but not the actual complaint — `render()` still contained real procedural HTML-construction logic (string concatenation, conditionals for the link-vs-copy-command branching). Moving the code from C# to JS didn't make it not-code.

**Round 2 (final): widgets are declarative, not code, on either side.**
- **A widget is an `.html` file (real Mustache-syntax template) plus an optional `.js` file (shared client-side behavior, only needed if the widget is interactive).** The fence block's body is real **YAML**, not the old ad-hoc `label | url` shorthand. Both are hand-rolled implementations (no external library dependency) but *real*, standard syntax — Mustache and YAML are language-agnostic specs with implementations in dozens of languages (`mustache.js`, `Stubble.Core`, etc.); using the real syntax means anyone who's used either before can read/write a Canary widget with zero Canary-specific knowledge, even though our own parser/templater are one-off.
- **`Canary.Core.Templating`**: hand-rolled `YamlParser` (a practical subset — block mappings, lists of mappings, scalars; no flow style/anchors/multi-line block scalars) and `MustacheTemplate` (`{{var}}` HTML-escaped, `{{#section}}`/`{{/section}}`, `{{^section}}`/`{{/section}}`; no partials, no unescaped output, no lambdas). `Canary.Core.Widgets.TemplateWidgetRenderer` is the entire "renderer" now — parse YAML, fill the template, done. **Jint is gone entirely** (removed from `Canary.Core.csproj`) — there's no more widget-authored code to execute at build time.
- **Interactivity moved from "generated once per instance" to "one shared script, referenced once per page."** The old approach regenerated the *entire* click/keydown/autoplay JS as a string on every single widget occurrence (visible in the raw HTML as sprawling inline `onclick=` attributes). Now a widget's template emits plain, data-only markup (`data-widget="slideshow"`, real `<img>` tags, no inline JS at all), and its `.js` file (if any) is copied once and referenced via `<script src="/js/widgets/<name>.js" defer>` — real, boring, readable JS using `document.addEventListener` with event delegation, not string-templated code. A newly-swapped-in widget instance (hybrid mode's fragment-fetch) is handled automatically by delegation; the one thing delegation can't cover (autoplay start on first image load, hiding nav for a single-slide show) uses a `MutationObserver` — the standard way to react to dynamically-inserted DOM content.
- **Discovery, not registration**, same principle as round 1: `SiteBuilder` scans `runtimeDistDir/widgets/` (built-in) and `<siteRoot>/widgets/` (site-authored, takes precedence on a name collision) for `*.html` (templates) and `*.js` (behavior) separately, keyed by filename. No config entry — reference the fence tag in content, and if a matching template exists, it's used. A page's shell gets a `{{widgetScripts}}` placeholder (new, alongside `{{title}}`/`{{content}}`/etc.) filled with `<script>` tags for every discovered behavior script, site-wide (v1 simplicity: every page references every widget's script if one exists anywhere on the site, not just pages that use it — a few extra small requests on pages that don't need a given widget, traded for zero per-page usage-tracking complexity).
- **Found and fixed two more real bugs by actually running things, not by review:** (1) the shell.html self-collision bug repeated itself — `downloads.html`'s own explanatory comment used literal `{{#items}}` syntax as documentation, which the templater dutifully executed as a real tag, corrupting output; fixed by describing the syntax in prose instead of writing it literally. (2) `ResolveUrl` was a genuine gap: with no widget-specific code left anywhere, nothing applied the root-relative-path fix to a YAML `url:`/`src:` field. **Resolved 2026-08-17**, same day: the user explicitly didn't want automatic field-name-based resolution ("not that interested in non-url fields being resolved by an automated system... a syntactical rule must be made"), so instead of guessing, an author opts in explicitly with a real YAML tag: `url: !url "content/games/x.png"`. `Canary.Core.Templating.UrlResolver` now holds the one shared implementation (extracted out of `MarkdownRenderer`, which used to have its own private copy — one implementation, not two, same principle as everywhere else in this section); `YamlParser` detects the `!url` tag on any scalar (top-level or inside a list item) and resolves it at parse time, before the value ever reaches the Mustache templater. A plain `url:`/`src:` with no tag is left untouched. Both widget templates' doc comments updated to show the tag; regression/unit-tested (`YamlParserTests`) and end-to-end tested through the real `SiteBuilder` pipeline (`SiteBuilderWidgetDiscoveryTests`).
- Verified end-to-end: real build against the `workspace/` dogfood site, real browser testing via claude-in-chrome (slideshow prev/next/autoplay-pause, downloads copy-button, all via the shared delegated scripts, zero console errors), plus unit tests for `YamlParser`/`MustacheTemplate` and an integration test proving the actual promise — a throwaway custom widget dropped into a test site's `widgets/` folder is picked up and rendered with zero registration, and its behavior script gets copied + referenced automatically.

**Still open:** whether `{{widgetScripts}}` should become per-page (usage-tracked) instead of site-wide. (Two other items that used to be listed here — client-side widget rendering for `spa` mode, and making the `!url` tag consistent between build-time and `spa` client-time — are moot now that `spa` mode has been removed entirely; see **Render modes**.)

**`canary widgets` / `canary widget <name>` CLI commands (2026-08-17).** Every widget's `.html` file now has a dedicated `<!--clipboard ... -->` comment block (separate from its main documentation comment) holding a ready-to-paste fence-block usage example — inferred from the request itself (the user asked for the marker before saying what it was for) as the reason for wanting one: a CLI command to look up a widget's usage without digging through its source. `canary widgets` lists discovered widget names (built-in + site-authored, via the same `Canary.Core.Widgets.WidgetDiscovery` now shared with `SiteBuilder` — extracted out to avoid a third copy of the discovery rule); `canary widget <name>` prints that widget's clipboard example via `Canary.Core.Widgets.WidgetClipboardExample`. **Print-only, not real OS clipboard** — deliberate: there's no cross-platform clipboard API in .NET itself (real clipboard access means either a Windows-only dependency (WinForms/WPF) or shelling out to a different tool per OS, with Linux not even having one universal option between X11/Wayland). A user who wants their real clipboard can pipe the output themselves (`canary widget slideshow | pbcopy` etc.) — Canary doesn't need to own that. Confirmed cross-platform-targetable while at it: both `.csproj` files target plain `net10.0` (not `net10.0-windows`), and nothing in the codebase (`HttpListener`, `FileSystemWatcher`) uses a Windows-only API — not yet actually run on Linux/macOS to verify, but nothing should block it.

**Bug found via user review of the live dogfood site, not by me:** the downloads widget's copy-command row had lost its `.copy-command-row` wrapper `<div>` during the template rewrite — `<code>` and the Copy `<button>` became direct children of `.copy-command` (a flex *column* container), so they stacked vertically instead of sitting side by side per `framework.css`'s `.copy-command-row` flex-row rule. Fixed by restoring the wrapper.

**That fix surfaced a real, more significant gap in the incremental-build system**, found while re-verifying it: `canary build` initially reported "reused unchanged = 6" after the template fix — the checksum-gating in `PageBuilder`/`SiteBuilder` only hashes the *markdown source*, never the widget template/behavior files a page's content references. Editing a widget's `.html`/`.js` does not invalidate the cache for pages that use it; only a full rebuild (or editing the markdown itself) picks up a widget change. Worked around here by clearing `output.dir` and rebuilding clean at the time — **fixed properly 2026-08-18, alongside implementing Content hooks (see that section)**, rather than left open.

**Widget CSS extracted out of `framework.css` into per-widget `.css` files (2026-08-18), caught by user review of the CSS itself.** The built-in `downloads`/`slideshow` widgets' styling had been hardcoded directly into the site's base `framework.css` since before this round's redesign even existed — which quietly broke the "built-in and site-authored widgets are discovered and treated identically" promise everything else in this section was built around: a site-authored widget had no equivalent place to put its own CSS, while the two built-ins got free styling nobody else could get. Fixed by giving widgets a third discovered file type alongside `.html`/`.js`: `runtime/widgets/downloads.css`/`slideshow.css` (extracted verbatim, no rule changes — they reference the same `--bg`/`--accent`/etc. tokens `framework.css` defines on `:root`, which cascade globally regardless of which linked file references them, so nothing needed to change functionally), `Canary.Core.Widgets.WidgetDiscovery` gets a third `"*.css"` call, `SiteBuilder` copies discovered stylesheets to `output/css/widgets/<name>.css` and fills a new `{{widgetStyles}}` shell placeholder with `<link>` tags (same site-wide-not-per-usage pattern as `{{widgetScripts}}`), and the widget checksum seed now covers `.css` too. `copy-widgets.mjs` updated to also copy `.css` into `runtime/dist/widgets/`. Verified: 129/129 tests (2 new, mirroring the existing `.js` coverage), and a real rebuild + browser check of `workspace/` confirming both built-in widgets render pixel-identical to before — the fix is purely about *where* the CSS lives, not what it says.

**Deliberately not done:** redesigning *how* a widget authors its interactivity (the inline `onclick`/`onload` string-building pattern itself is still hand-rolled JS-as-strings, just now in one place instead of two) — that was explicitly flagged as a separate, larger question and left alone for now.

## Content hooks — per-page markdown preprocessing (implemented 2026-08-18)

Motivating case, from the user: functionality that should apply to *many* pages — a breadcrumb at the top, a "Return to Blog" link at the bottom of every post — without copy-pasting a widget fence block into every markdown file. Doing that in the content itself defeats the actual goal, keeping site behavior and content data separate (same spirit as why widgets exist at all). A **hook** is an external command that receives a page's raw markdown on stdin and returns transformed markdown on stdout, run once per page at build time, before that markdown reaches the renderer.

**Why build time, not per-request/in-browser:** hooks are an arbitrary external command — no browser equivalent exists, so they can only ever run once, at build time, before the transformed markdown reaches the renderer. This was actually the realization that killed off `spa` mode entirely (see **Render modes**, **Resolved**): `spa` used to ship raw markdown to the client and render it there, which would have meant either giving hooks a client-side escape hatch that doesn't make sense for an arbitrary external command, or `spa` prerendering anyway and losing its own reason to exist. With `spa` gone, hooks only ever need the one `hybrid`/`static` prerendering path that already exists — no second code path to keep in sync, no "does this also need a JS port" question to re-litigate for every future feature.

**`.hooks.json` auto-creation goes deeper than `.nav.json`'s does.** `.nav.json` only auto-creates at *top-level* content directories, because `ManifestBuilder.BuildNav` only ever walks one level deep — nav's data model is flat categories with children, so that's all it needs. Hooks have no such shortcut: since application is deliberately non-recursive with no inheritance (see above), a directory's hook list only ever covers `.md` files directly inside it, at *any* depth. So `.hooks.json` auto-creation has to mirror `ContentScanner`'s full recursive walk (`SearchOption.AllDirectories`), not `ManifestBuilder`'s one-level walk: every directory containing at least one `.md` file directly inside it, at any depth, gets an empty self-documenting `.hooks.json` if missing — same backfill-on-missing-fields behavior `.nav.json` already has, just scoped deeper.

**Registry (definition) vs. application are deliberately separate concerns:**
- **Definition** — a `hooks` dictionary (name → command) in `config.json`, alongside `site`/`content`/`theme`/`widgets`. One central place, since this part genuinely is site-wide, not per-directory.
- **Application** — a new **`.hooks.json`** per content directory, sitting alongside `.nav.json` but a **separate file**, not a section bolted onto it. Considered and rejected merging into `.nav.json`: nav visibility and hook application are orthogonal axes, the same reasoning already applied in Phase 3 to keep `SitemapBuilder` independent of the nav tree ("nav visibility and search-engine discoverability are independent axes, not the same thing"). Merging would also mean `ManifestBuilder` (which owns `.nav.json`'s read/backfill/self-documentation today) either has to learn about hooks, or some other module has to co-own that file's schema for fields it doesn't otherwise touch — and `.nav.json`'s name would quietly stop meaning what it says.
- **No cascading/inheritance down the content tree.** A directory's hook list is exactly what its own `.hooks.json` declares — nothing inherited from a parent directory. Considered and rejected inheritance explicitly: it's the same implicit-behavior problem already resolved once for widgets (the `!url` tag decision) — a page's behavior shouldn't depend on something declared three directories up that isn't visible from where the page actually lives. The tradeoff is real repetition for a hook meant to apply broadly (re-declaring `"breadcrumb"` in every directory that wants it), accepted deliberately in favor of every directory's behavior being visible without tracing up the tree.

**Execution model:** a page's applicable hook names run in their declared array order, chained — one hook's stdout becomes the next one's stdin, and the final result is what the renderer sees. A hook command exiting non-zero fails the whole build outright — no silently-broken output, matches how most pre/post-script toolchains already behave.

**Deliberately deferred, not part of this round** (same "revisit only if a real need shows up" reasoning as the plugin system):
- Whole-build pre/post hooks (e.g. running a site's own asset build before `canary build` starts) — no concrete use case yet, unlike the per-page content case above.
- A "disable an inherited hook for this subtree" escape hatch — moot without cascading in the first place; nothing to disable if nothing is inherited.

Config shape:
```json
{
  "hooks": {
    "breadcrumb": "tools/breadcrumb.sh",
    "return-to-blog": "tools/return-to-blog.sh"
  }
}
```

`.hooks.json` (per content directory):
```json
{ "hooks": ["breadcrumb"] }
```

**Implementation, and the checksum-gating fix that came with it (2026-08-18).** New `Canary.Core.Hooks` namespace, kept deliberately separate from `Canary.Core.Manifest` per the design above: `HooksOverride` (the `.hooks.json` data model), `HooksOverrideFile` (load + auto-create, mirroring `.nav.json`'s pattern but recursing to every depth), `HookRunner` (chains a page's applicable hooks via `System.Diagnostics.Process`, piping stdin/stdout; also exposes a separate cheap `ChecksumSeed` that never actually executes anything). `SiteBuilder` wires it in: `.hooks.json` auto-creation runs once per build off the same route list `ContentScanner` already computed (not a second filesystem walk); each route resolves its directory's applicable hooks and only actually runs them on a cache miss.

That last point is the other half of this work — **the checksum-gating known bug (widgets *and* hooks) got fixed in the same pass**, as planned. `PageBuilder.BuildPage` gained an `extraChecksumSeed` parameter (folded into the hash alongside the markdown source) and a `transformSource` callback (applied only on a cache miss — hooks are potentially expensive, so unconditionally running them just to decide whether to skip them would defeat the entire point of the gate). `SiteBuilder` computes one combined hash of every discovered widget file's content, once per build (same site-wide-not-per-page-usage tradeoff already made for `{{widgetScripts}}`), plus each route's hook-specific seed (hook names + their registered commands + the referenced script's own content when the command resolves to a real file under the site root). The embedded HTML comment was renamed `source-checksum` → `content-checksum` to honestly reflect that it no longer covers just the markdown source (`PageBuilder`'s regex, and the "Incremental builds" section below, both updated to match).

Three real bugs found via actual testing, not by inspection, same standard as everywhere else in this project:
1. **`cmd.exe`'s command-line quoting is two bugs deep.** A hook command shaped exactly like the config example (`"tools/breadcrumb.sh"`) failed outright the first time it was actually run: `cmd /c tools/breadcrumb.sh` gets misparsed because cmd's switch scanner keeps looking for more `/x`-shaped switches anywhere after `/c`, so the forward slash inside the path reads as a second switch. The obvious fix — wrapping the whole command in quotes — *also* failed, because cmd only preserves quotes under specific conditions (see `cmd /?`), one of which requires whitespace *inside* the quoted string; a bare path has none, so cmd silently strips the quotes and the bug comes right back. Fixed by prefixing with `call ` (`/c "call tools/breadcrumb.sh"`), which reliably satisfies that whitespace condition regardless of what the command actually is — verified empirically against real `cmd.exe` invocations (including that exit codes still propagate) before landing it, not just reasoned about.
2. A test-fixture gap, not a product bug, but worth noting since it briefly looked like the checksum fix itself was broken: `SiteBuilderHooksTests`'s minimal `shell.html` fixture (copied from an existing test file) didn't include a `{{checksum}}` placeholder, so the checksum comment was never embedded in output at all — every build looked like a cache miss regardless of what changed. Confirmed as a test-only issue by reproducing the exact same symptom with the real CLI against a similarly minimal `shell.html`.
3. **A real race in `HookRunner.Execute`, surfaced later by an intermittently-failing test.** Writing to `process.StandardInput` after the child process has already exited (e.g. a hook command like `exit /b 1` that exits immediately without ever reading stdin, or any fast-failing/input-ignoring hook) throws an `IOException` (broken pipe) that masked the real, intended error — a clean "hook exited non-zero" message. Fixed by wrapping the stdin write in a `try`/`catch (IOException)`: a broken pipe there is an expected, benign condition, not the actual failure signal, which is the exit code checked immediately after. Verified by running the affected test 5 times in a row after the fix (it's a timing-dependent race, so a single green run doesn't prove much on its own).

Verified: 127/127 tests passing (26 new — `HooksOverrideFileTests`, `HookRunnerTests`, `SiteBuilderHooksTests`, plus new `PageBuilderTests` coverage for `extraChecksumSeed`/`transformSource`), including end-to-end proof through the real `SiteBuilder` pipeline that editing a widget *or* a hook script now correctly invalidates just the affected page's cache, and that an unrelated no-op rebuild still reuses everything. Also dogfooded for real against `workspace/`: `.hooks.json` auto-created correctly at both `content/` and `content/characters/` (any-depth, not just top-level); a real `curtain` hook (a `.cmd` script appending "— Curtain. —") declared in `content/.hooks.json` applies to the home and Synopsis pages but — confirmed live in a browser — correctly does *not* apply to `characters/frederic/` (no cascading, exactly as designed), zero console errors.

## Project configuration file (JSON)

Format is JSON (matches the existing `manifest.json` convention, zero new parsing dependency). v1 shape — one config per environment (no dev/prod split), nav/routes always derived from `content.root` + generated manifest (never redeclared in config), single flat content root:

```json
{
  "site": { "name": "...", "baseUrl": "https://..." },
  "content": { "root": "content/" },
  "output": { "dir": "docs" },
  "renderMode": "hybrid",
  "nav": { "depth": 1 },
  "theme": { "shell": "templates/shell.html", "base": "css/framework.css", "theme": "css/theme.css" },
  "widgets": { "copyDefaultsOnInit": true, "preferBuiltIn": false },
  "hooks": { "breadcrumb": "tools/breadcrumb.sh" }
}
```

No `deploy` field yet — see **Core built-in functionality** above for why: `output.dir` is the entire deploy story for git-served hosts. A remote-push config block (FTP/SFTP target, credentials reference, etc.) gets added once that feature actually exists, not speculatively now.

**`nav.depth` (implemented 2026-08-18) — how many directory levels deep the generated nav *menu* recurses**, default `1`. This was a real gap, not a deliberate v1 scope choice: `ManifestBuilder`'s nav-tree builder had been hardcoded to one level ever since it was ported from consoland's own `build-manifest.cs` — a fine default for consoland's genuinely flat site, but a site-specific assumption that had just been sitting there unexamined, not a universal rule. It broke down the moment a site needed real nested structure (the motivating case: Canary's own future docs site, e.g. `docs/guides/widgets.md` — a page two directories deep that the nav tree would otherwise never surface at all, even though `ContentScanner` already builds and serves it as a real page regardless of nav depth). `<= 0` means unlimited depth.

Implementation: `ManifestBuilder.BuildDirectoryNavItem` now recurses into a directory's own subdirectories exactly the same way it already handled the directory itself — a nested directory becomes a nav item with its own landing page/children, sorted alongside its sibling *files* in one dropdown (priority-then-title, same rule the top level already used, now applied uniformly at every level). `.nav.json` auto-creation, which used to be implicitly capped at top-level directories for the same "nav tree only goes one level" reason, now reaches exactly as deep as the nav tree itself does — no second, separately-tracked depth limit to keep in sync.

The client side needed real work too, not just a pass-through: `runtime/ts/nav.ts`'s renderer used to flatten every dropdown child into a plain `<a>`, with no recursion at all — a deeper `NavItem.Children` in the JSON manifest would have been silently truncated by the browser even with the C# side fully fixed. Rewritten so a child with its own children renders as a nested flyout submenu (`.nav-subitem`, hover/focus-gated independently of its parent dropdown) instead of losing its grandchildren; `updateActiveNav` rewritten to walk up the DOM from whatever depth actually matched, marking every ancestor level active, rather than only ever checking one level. A depth-1 site's markup and behavior are byte-for-byte unchanged by any of this — the new code paths only ever activate once a `NavItem` genuinely has grandchildren, which never happens at `nav.depth: 1`.

**The submenu's "further" chevron took three attempts to actually fix, worth recording because the first two both looked correct and weren't** — a real lesson in verifying against the DOM, not a screenshot. User review caught it first: the chevron indicating a row expands further was rendering flush against the label text. Attempt 1 assumed `justify-content: space-between` just needed slack width it didn't have, and swapped to a fixed `gap` — looked unchanged when re-checked, still touching. Attempt 2 theorized a `::after` pseudo-element merges into the same anonymous flex item as its adjacent text (so `gap` would have nothing to apply between them) and switched the chevron to a real sibling `<span>` — *still* touching, confirmed via a zoomed screenshot in a brand-new tab (ruling out cache). Verified this time by measuring the actual rendered gap between the two spans' `getBoundingClientRect()`s (8px, exactly `0.5rem`) rather than trusting another screenshot.

## CLI surface

- `canary init` — scaffold a new site. Two modes: pass an existing `config.json` to scaffold from directly, or run interactively and be prompted for each option one at a time (site name, base URL, render mode, content root, ...).
- `canary build` — full build: manifest generation, chrome re-stamp (always), content render (checksum-gated per **Incremental builds**, below), sitemap/robots generation, all written to `output.dir`. For a git-served host like GitHub Pages, this *is* the deploy step — the site owner commits/pushes `output.dir` themselves.
- `canary serve` — local dev server against the config, for iterating before committing/pushing.
- *(later, optional)* a remote-push verb for hosts that need file transfer rather than a git-served folder (FTP/SFTP) — not part of v1, see **Core built-in functionality** above.

## Incremental builds (carried over, still the plan)

- Chrome (header/nav/footer skeleton + script/style tags) is **unconditionally re-stamped every build** — it's cheap and always current from one source template, so there's no "did it change" case to special-case.
- Content rendering (markdown → HTML) is the expensive, diff-noisy part, so it's the only thing gated: each generated page embeds a `<!-- content-checksum: sha256:<hash> -->` marker; the build step compares that to a freshly computed hash and skips re-rendering (and re-running any applicable hooks) when unchanged. The hash covers more than just the markdown source — see **Content hooks**'s implementation notes — which is why the marker's name changed from the original `source-checksum`: it also folds in every discovered widget file's content and, per page, that page's applicable hooks and their registered commands, so editing a widget or a hook correctly invalidates the cache for pages that use it.
- `canary build` writes only changed files into `output.dir`, rather than wiping and recreating the whole directory every time — keeps git diffs against `output.dir` small and meaningful.

## Known bugs, tracked but not yet fixed

- **Stale hash + real path mismatch on a bookmarked/shared mid-navigation URL (hybrid mode).** A URL like `/characters/frederic/#/characters/mabel` (real path from one page, hash from client-side nav to another) opened fresh: the server can't see the fragment, so it serves Frederic's prerendered page; the client router reads the hash as "mabel" and — because `hybrid-router.ts`'s `initialLoad` skip-fetch logic assumes served content always matches the current hash — leaves Frederic's content on screen while the nav highlights Mabel, until the next click. Not an SEO/crawler issue (fragments are never sent to or indexed by crawlers — see chat 2026-08-16), purely a UX inconsistency for a human who bookmarks/shares mid-navigation. Deliberately left unfixed for now, at the user's call.

## Open questions still unresolved

- **Remote-push (FTP/SFTP) config shape and credential handling** — deferred along with the feature itself (Phase 6), but worth noting credentials-in-a-JSON-config is a real question to get right (env var reference vs. OS credential store vs. something else) whenever that phase starts.

Root is exempt since its content already matches hash `""`/`#/`. Would also skip sitemap/robots generation for a site using this flag, matching `spa`'s old "not crawlable, that's fine" character.
  - **Real interaction with the existing "stale hash + real path mismatch" known bug**: that bug is currently rare (only hit on a bookmarked/shared mid-navigation URL) and deliberately left unfixed. The redirect scheme above would make it the *normal* case instead of a rare one — every visit through the redirect cold-loads root's own content while the hash already points somewhere else, exactly the mismatch that bug describes. Building the redirect flag would mean actually fixing `hybrid-router.ts`'s initial-dispatch logic (stop assuming served content matches the hash-derived route on first dispatch; check and fetch when it doesn't) rather than leaving it deferred.

- **`spa` mode removed entirely (decided and done, 2026-08-18).** Surfaced while designing **Content hooks**: hooks are an arbitrary external command with no browser equivalent, so they can only ever run at build time — which meant `spa` mode would have had to prerender to get hooks working at all, at which point it was no longer meaningfully different from `hybrid` in *how content gets built*, only in navigation policy. Once that justification was gone, the user's call was direct: "Its time for SPA to die." Removed: the `RenderMode.Spa` enum value, `SiteBuilder.BuildSpa`, `RuntimeAssetManifest`'s spa entry, `runtime/ts/spa-router.ts`, `runtime/ts/markdown.ts` (the client-side markdown renderer — `spa` was the only mode that ever ran it in the browser, so nothing needs it now), and the spa-specific test cases in `ConfigLoaderTests`/`SiteBuilderSeoTests`. `SiteBuilder.CopyContentAssets` and sitemap/robots generation both simplified since there's no longer a mode that needs different treatment (markdown is now unconditionally excluded from the content copy; SEO files are now unconditionally written). This also retired two other standing gaps for free: the "Still open" client-side widget-rendering gap from **Widget system** (moot — widgets only ever render at build time now, in every mode) and the "does the `!url` tag work client-side" question (same reason). Verified: full rebuild + `dotnet build`/`dotnet test` (101/101 passing, down from 103 — the two spa-only tests were removed, not broken) + `npm run build` (TS compiles clean without the deleted files) + a full rebuild of the `workspace/` dogfood site in `hybrid` mode, all green. `spa`'s old hash-only-navigation UX is still recoverable later as a `hybrid` config flag if a real need shows up — see **Open questions**.
- **Checksum-gating didn't track widget files (and would have missed hooks too)** → fixed 2026-08-18, alongside implementing **Content hooks** as planned (fix both gaps together in one pass, not twice). Full details, including the two real bugs found while testing the fix (a `cmd.exe` quoting issue and a test-fixture gap), are in that section above.
