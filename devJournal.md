# Canary — Development Journal

Raw material for a blog post, not the blog post itself. Chronological, quote-heavy, and honest about the parts that went sideways before they went right. Assembled 2026-08-18 from git history (both `canary` and its parent project `consolandWebsite`), `PLAN.md`, `MostImportantControversy.md`, and the actual development conversation; kept current through 2026-08-25.

---

## Act 0: Consoland, before any of this was a problem (Aug 14–16)

Canary didn't start as a framework. It started as a personal site.

`consolandWebsite`'s original plan (`consolandWebsite/PLAN.md`, written 2026-08-14) is refreshingly small in scope:

> The user wants a personal site to publish CLI utilities/games (mostly served as downloadable MSI installers) as a lightweight, hand-rolled wiki: drop a markdown file in a folder, it becomes a page.

Three decisions, locked in from day one and never really revisited until Canary existed: hand-written TypeScript for the browser (no framework, no markdown library), a C# console app for everything else (scan content, compile TS, assemble output, `git add/commit/push`), and GitHub Pages serving a `docs/` folder. "No framework" wasn't a slogan — it was load-bearing. The whole point was a hand-built wiki, not an app.

Over the next two days, consoland actually shipped, one commit at a time:

```

d71ba18  added domain registration instructions
d76d954  great progress
8582640  Create CNAME
9e7fec0  Test site is live
13c233c  Merge branch 'main' of github.com:haberling/consolandWebsite
f308bcd  The old blog posts are here now.
28243f4  Imaged added in to blog post

a13d598  tessalate page added to content / not site

13d524e  removed last example page, added google analytics tag
```

By the last commit (Aug 16, 18:56), consoland was a real, live, small site: old blog posts migrated over, a Tesselate game page with a slideshow, Google Analytics wired up. The entire hand-rolled stack — router, markdown renderer, the two content widgets, the C# manifest/deploy tooling — was 866 lines across five files. Genuinely tiny. Genuinely "no framework."

It used **hash routing**: `consoland.net/#/games/tesselate`. Client-side JS fetches the right markdown file and renders it into `#app`. Zero server config needed — GitHub Pages just serves `index.html` for every request, and the fragment after `#` never even reaches the server. That property is *why* hash routing got chosen in the first place: no rewrite rules, no server-side anything, works identically whether GitHub Pages or literally any static host serves the files.

It also meant the site was **functionally invisible to search engines**. A crawler doesn't execute the hash router; it never sees anything past `index.html`. A sitemap of hash URLs would list N entries that all resolve to the exact same document — worse than useless, actively misleading to a crawler.

That's the wall the project hit on the evening of Aug 16, less than three hours after the last consoland commit.

## Act 1: The pivot (Aug 16, evening)

The fix everyone reaches for here is prerendering — generate a real static HTML file per route at build time, so a sitemap's `<loc>` points at something a crawler can actually fetch and read. That much wasn't controversial. What *was* a real decision: **do this as a patch to consoland, or pull the reusable parts out into their own thing first?**

The call was to extract early. Canary's very first commit message says it plainly:

> Bootstraps the Canary repo with the design plan carried over from the consolandWebsite split-out discussion, plus baseline open-source scaffolding.

And the opening line of that first `PLAN.md`, written before a single line of prerendering code existed:

> Canary is the site-engine being split out of `consolandWebsite`: the hand-rolled TypeScript runtime (hash router + markdown renderer + nav-from-manifest) and the C# build/deploy tooling, minus that site's actual content and branding. It was born out of a design discussion about making the markdown-wiki approach crawlable by search engines without losing the "no framework" hand-built character of the original site.

That last clause matters as much as the SEO problem itself: the fix had to preserve the *character* of consoland, not just its function. Bolting a heavyweight SSG onto a deliberately tiny hand-rolled site would have solved the crawler problem while killing the actual point of the project. Canary's whole design constraint from minute one was "generalize this, don't replace it."

The original scope was narrow and specific — not "build a framework," but five concrete mechanisms:

1. Don't point a sitemap at raw `.md` files or hash-fragment URLs — a sitemap `loc` has to be a real, directly-browsable page.
2. Prerender to real static paths, but *keep* the hash-router SPA for in-app navigation once JS loads — additive, not a rewrite.
3. Header/nav/footer chrome is an identically-referenced skeleton, not duplicated content.
4. Chrome is unconditionally re-stamped every build; only content-rendering is checksum-gated (cheap to redo the shell every time, expensive and diff-noisy to redo the render).
5. Incremental build via a per-page source checksum embedded directly in the output HTML.

Everything else — the render-mode system, the widget architecture, hooks, the whole idea of "a framework" rather than "a build script" — grew out from that narrow seed over the following two days.

## Act 2: Bootstrap (Aug 16, 19:54 → 21:29)

Ninety minutes after the initial commit, "Skeleton added" landed: the actual solution structure (`Canary.slnx`, `src/Canary`, `src/Canary.Core`, `tests/Canary.Core.Tests`), the config loader and its schema, and — tellingly — the *entire consoland TS runtime ported over verbatim first* (`main.ts`, `markdown.ts`, `router.ts`, both widgets, `framework.css` split off from consoland's `style.css`). 1,660 lines added in one commit.

This is the "extraction" phase doing exactly what extraction means: get the working thing copied over and compiling clean *before* changing anything about how it works. Nothing architecturally new yet — just consoland's guts, minus consoland's branding, sitting in a new home.

## Act 3: The marathon (Aug 16, 21:29 → Aug 17, 02:15)

The single biggest commit in the whole project's history — "all but canary init" — landed at 2:15 AM. Nearly five hours, one sitting, and by the diff stat it's not close: `SiteBuilder`, `PageBuilder`, `ContentScanner`, the whole `Canary.Core.Manifest` namespace, the markdown renderer, the YAML parser, the Mustache templater, the static file server and dev-mode watcher, sitemap/robots generation, and — the part that took the longest and detoured the hardest — the entire widget system, twice.

### The bug that wasn't really about the bug

It started as a routine code review. Asked to look at `SlideshowWidgetRenderer.cs` (the just-ported C# build-time widget renderer), a real bug turned up fast: `RenderSlide` built its `<img src="...">` attribute directly from the slide data, never routing it through `ResolveUrl` — the root-relative-path fix that had *already* been added for ordinary markdown links earlier that same session. A slideshow image written as `content/games/images/x.png` would render exactly as typed, no leading slash, and break the instant the page lived anywhere but the site root. `DownloadsWidgetRenderer` had the identical gap.

It had slipped through for a boring, honest reason: the smoke-test content was only ever inspected as raw HTML text, never actually loaded in a browser, and the dogfood site's own slideshow happened to use absolute `https://` URLs that never needed resolving in the first place. Nothing exercised the code path.

That would have been a two-line fix. It wasn't the point. `MostImportantControversy.md` — written live, mid-argument, specifically so the disagreement wouldn't get lost — records the actual objection in the user's own words:

> "I meant the whole method behind widgets, I dont like it, a widget needs to be something a lot more readable than this in its own right."

The vision underneath that: a site author should be able to write their own widget, drop it in a `widgets/` folder next to their content, reference it from a markdown fence block, and have it just work — no editing Canary's own source, no recompiling Canary itself. And the TypeScript side already *had* this property. `markdown.ts`'s widget dispatch was already `import(\`./widgets/${name}.js\`)` by pure filename convention, no registry — its own comment said so directly: *"Adding a new widget is just adding a new file there... this file never needs to change."*

The C# port had quietly regressed that. `SlideshowWidgetRenderer`/`DownloadsWidgetRenderer` were hardcoded into a dictionary literal — a site author couldn't add a third widget without editing Canary's own source and recompiling it. Not a deliberate choice. Just a thing that fell out of porting TS to C# without carrying the *property*, only the *behavior*, across the language boundary.

### Why the obvious fix wasn't available

Getting true "drop a `.cs` file in, it just works" parity on the C# side means compiling and running arbitrary C# at build time. That's architecturally identical to a build-time plugin system — which had *already* been explicitly cut from scope earlier in the same session, on the grounds that it was speculative, no concrete use case yet. Reviving that exact mechanism to solve widgets, quietly, under a different name, would have been exactly the kind of sideways scope-creep the project was trying to avoid on purpose.

Two real options went on the table instead: revive Roslyn scripting scoped specifically to widgets (true TS-side parity, no sandboxing, same tradeoffs as the original cut plugin idea), or a precompiled-DLL-plus-reflection-scan approach (avoids re-opening "run arbitrary source at build time" at all, but now a widget author needs the .NET SDK and knows how to build a class library — a real barrier, not just authoring a file).

### Round 1 — fixed the wrong half

The first resolution: widgets as plain `.js` files (not TypeScript), executed at build time via **Jint**, an embedded JS interpreter. Discovery by scanning a folder, no registry. This sidestepped the Roslyn-vs-DLL question entirely by not running C# at all — and it genuinely fixed "one implementation instead of two," since now both the browser and the build-time renderer executed the exact same widget code.

It didn't fix the actual complaint. `render(title, body)` still *was* real procedural code — string concatenation building up HTML, conditional branches for the link-vs-copy-command split. Moving that code from C# to JS didn't make it stop being code. The user caught it directly: *"it looks like how to build knowledge still sits inside the renderer."*

### Round 2 — declarative on both sides

The real fix, and the one that stuck: a widget is an `.html` file — a genuine Mustache-syntax template, not a Canary-specific format — plus an optional sibling `.js` file for shared client-side behavior. The fence block's body became real YAML instead of an ad-hoc `label | url` shorthand. Both parsers are hand-rolled (no external dependency, matching the "no framework" ethos everywhere else in this project), but they implement *real, standard, portable syntax* — anyone who's touched Mustache or YAML before can read or write a Canary widget with zero Canary-specific knowledge.

`Canary.Core.Widgets.TemplateWidgetRenderer` became the entire "renderer," full stop — parse the YAML, fill the template, done. Jint got ripped back out, this time for good, because there was no widget-authored *code* left anywhere to execute.

Interactivity moved with it: instead of regenerating an entire click/keydown/autoplay script as an inline string on every single widget occurrence (visible in the raw HTML as sprawling `onclick=` attributes), a widget's `.js` file — when it has one — gets copied once and referenced once per page via `<script defer>`, using real `document.addEventListener` event delegation instead of string-templated code.

Two more real bugs turned up building this, both found by actually running things:

- **The doc-comment trap.** `downloads.html`'s own explanatory comment used the literal syntax `{{#items}}` to describe what the section did — and the templater has no concept of "this text is just documentation." It executed the comment as a real tag, corrupting the output. (This had already bitten the shell chrome template once before this; it bit a widget's own doc comment the exact same way.) Fixed by describing the syntax in prose from then on, never writing the literal characters in a comment.
- **The `!url` question, and a real, sharp design line drawn in response.** With no widget-specific code left anywhere, nothing applied the root-relative-path fix to a YAML `url:`/`src:` field anymore — the exact bug this whole detour started from was technically still unfixed. The instinct was to auto-resolve any field literally named `url` or `src`. The user's reaction, direct and immediate:

  > "im just not sure thats a problem" ... "im not that interested in non url fields being resolved by an automated system... a syntactical rule must be made in how arguments are passed to widgets."

  The objection wasn't the bug fix — it was *guessing* based on a field's name. What if a field happens to be called `url` but genuinely shouldn't be resolved? What if a field means a URL but isn't named that? The resolution: a real YAML tag, `!url`, that an author writes explicitly on the one value that needs it (`url: !url "content/games/x.png"`). Standard YAML syntax (`!name` tags are real — `!Ref` in CloudFormation, `!include` elsewhere), opt-in rather than inferred. This exact incident became a standing principle for the rest of the project: when a design has to choose between guessing from context and requiring an explicit marker, default to the explicit marker, every time, even when guessing would be less typing.

By the end of that five-hour commit: 103 tests passing (up from 8 at the very start of the day), full render pipeline across three modes, `canary serve`, sitemap/robots generation, and a widget system that had been fought over, gotten wrong once, and rebuilt properly.

## Act 4: Dogfooding for real (Aug 17)

Up to this point almost everything had been verified as generated files on disk, never actually *looked at*. That changed. A real dogfood site got built — an informational site about Gilbert & Sullivan's *The Pirates of Penzance*, home page with a slideshow of real Wikimedia Commons production posters, a synopsis page, a `characters/` section with dropdown nav — and driven through an actual Chrome browser via the claude-in-chrome extension for the first time.

It found a real bug immediately: landing cold on a real prerendered URL (typed directly, or reached via a full-page in-content link) has no hash fragment at all. `hybrid-router.ts` only ever read `location.hash` to know the current route, so it silently misread every such cold load as the site root — highlighting "Home" in the nav instead of the actual page. Content was never wrong (the initial-load branch never touched `#app`), only the nav highlight — but it was a real, user-visible bug that file-level inspection had completely missed. Fixed by seeding the router's notion of "current path" from `window.location.pathname` before the hash-derived value (meaningless on a cold load) could stomp it.

`canary serve` found its own bug the same way, and it was a nastier one: the file watcher initially watched everything except `output.dir` — but `ManifestBuilder` unconditionally rewrites `content/manifest.json` back into the *source* tree on every build. Every rebuild retriggered the watcher, which triggered another rebuild, forever. This wasn't a hypothetical — it became an actual runaway process that had to be `taskkill`ed. The fix generalized past the specific case: the watcher now pauses itself while its own callback runs (plus a short grace period after, for filesystem notifications that arrive slightly late), so it can never react to its own writes regardless of where in the tree they land.

The `canary widgets`/`canary widget <name>` CLI commands landed the same day — each built-in widget got a `<!--clipboard ... -->` comment block holding a ready-to-paste usage example, extracted at request from the widget's own `.html` file, so looking up correct syntax never requires reading the template source. Print-only, deliberately not real OS clipboard access — no cross-platform clipboard API exists in .NET without a Windows-only dependency or per-OS shelling out, and piping the output yourself gets nearly all the value for none of the cost.

A user review of the live dogfood site (not automated testing) caught one more real bug: the downloads widget's copy-command row had lost its wrapper `<div>` during the Round 2 rewrite, so the code block and Copy button stacked vertically instead of sitting side by side. Small fix — but re-verifying it surfaced something much bigger: after the fix, `canary build` reported "reused unchanged = 6" — the incremental-build checksum only ever hashed the *markdown source*, never the widget files a page's content actually depended on. Editing a widget silently did nothing until a full clean rebuild. Logged as a known bug, deliberately not fixed on the spot — it would matter more once there was a second thing (beyond widgets) that could invalidate a page's cache, and fixing both gaps in one pass beat touching that code twice.

## Act 5: spa/static dogfooding, and the bug that foreshadowed the ending (Aug 17)

The remaining two render modes got the same real-browser treatment. `static` came back clean. `spa` didn't: clicking "Characters" in nav showed a 404-style "Not found" page instead of the real content. Root cause: `spa-router.ts`'s route-to-file mapping only ever special-cased the site's root route; every other route just joined its path segments, which works for a leaf page but not for a *directory's own landing page* (`characters/index.md`, which the build-time convention already knew to treat specially, but the client-side router never had that memo). Fixed with a leaf-then-directory-index fallback fetch, verified live in the browser.

It's worth noting in hindsight: this was the second time in two days that *the exact same convention* had to be independently reimplemented on the client side and had drifted out of sync with the server side. That pattern was about to matter a lot more than one bug fix.

## Act 6: "lets have a conversation so you know what I mean" — designing hooks (Aug 17–18)

The next feature request came in deliberately unhurried: *"lets have a conversation so you know what I mean"* about "toolchaining." What followed was a real back-and-forth, not a spec dump — narrowing from "toolchaining" down to something concrete: a way to apply functionality (a breadcrumb, a "Return to Blog" link) across *many* pages, without copy-pasting a widget fence block into every markdown file by hand. That would defeat the entire point of separating site behavior from content data.

The design that emerged, refined turn by turn:

- A **hook** is an arbitrary external command. A page's raw markdown goes in on stdin, transformed markdown comes back out on stdout. Run once per page, at build time, before the markdown reaches the renderer.
- **Definition and application are deliberately separate.** Hook *commands* live once, centrally, in a `hooks` dictionary in `config.json`. Hook *application* — which directories actually run which hooks — lives in a new, separate `.hooks.json` per content directory.
- Considered and explicitly rejected: folding hook application into the existing `.nav.json`. The reasoning traced straight back to a decision already made in Phase 3 (keeping `SitemapBuilder` independent of the nav tree, since nav visibility and crawler discoverability are orthogonal concerns) — hooks were a third orthogonal axis, and merging them in would mean `.nav.json`'s own name would quietly stop meaning what it said.
- Considered and explicitly rejected: letting a directory's hooks cascade down to its subdirectories. This is the same principle the `!url` tag decision established a day earlier, applied again: a page's behavior shouldn't depend on something declared three directories up that isn't visible from where the page actually lives. The tradeoff — real repetition if a hook needs to apply broadly — was accepted on purpose.

And then, mid-design, the conversation took the turn that mattered most:

> "so, ok, in a sense, as you im sure imagine, this sorta breaks the whole idea of SPA mode, because its now still pre-rendering, but I dont want to limit how hooks can be written to something that can somehow be run in the javascript, so maybe we need to rethink spa mode in general..."

Hooks are an arbitrary external command — there's no browser equivalent, full stop, for any language a hook author might reach for. That meant `spa` mode would either need its own special-cased client-side hook mechanism that fundamentally couldn't exist for an arbitrary command, or it would need to start prerendering too — at which point it stopped being meaningfully different from `hybrid` in how content actually got built, only in navigation policy.

Asked for a straight pro/con on dropping `spa` entirely, the honest tally leaned hard toward "drop it": its whole reason to exist (client-side rendering without a build step) had just evaporated, and keeping it around would mean re-solving "does this also need a separate JS implementation" for every single future feature, forever — as `spa`'s own directory-index bug from a day earlier had already previewed. The user's counter-offer was sharp: recover most of `spa`'s old feel later, if it's ever actually needed, as a lightweight redirect-to-hash flag on `hybrid`, rather than as a whole separate rendering pipeline. Logged as a genuine future consideration, not built.

Then, once that was settled:

> "Ok now that we have Spa recovery in future considerations, Its time for SPA to die."

## Act 7: The purge (Aug 17, 21:40 → Aug 18, 00:10)

`spa-router.ts` had gotten one more update at 21:40 (folding in the day's directory-structure fixes) before, less than three hours later, getting deleted along with everything else `spa`-specific: the `RenderMode.Spa` enum value, `SiteBuilder.BuildSpa`, `RuntimeAssetManifest`'s spa bundle entry, `runtime/ts/markdown.ts` (the client-side markdown renderer — the *only* thing that had ever run it in a browser was the mode that had just been deleted), and the spa-only test cases. The commit message doesn't pretend otherwise:

> `SPA mode removed, because render toolchain renders it, lol, pointless`

The deletion turned out to retire two other standing problems for free: the long-open "spa mode needs its own client-side widget renderer" gap (moot — every widget renders at build time now, in every remaining mode) and the "does `!url` need to work client-side too" question (same reason). 101 tests passing afterward, down from 103 — the two removed tests were deleted along with the feature, not broken.

## Act 8: Hooks, for real (Aug 18, 00:42)

With `spa` gone, hooks only ever needed the one prerendering path that already existed. Implementation landed less than an hour after the removal commit: a new `Canary.Core.Hooks` namespace (`HooksOverride`/`HooksOverrideFile` for the `.hooks.json` side, `HookRunner` for actually chaining and executing hooks via real subprocesses), wired into `SiteBuilder` — and, as planned a day earlier, the widget-and-hook checksum-gating fix landed in the exact same pass rather than as a second, separate change.

Two more real bugs, found by actually running the thing rather than by reading the code:

- **`cmd.exe`'s quoting is two bugs deep.** A hook command shaped exactly like the design's own example — `"tools/breadcrumb.sh"` — failed the very first time it actually ran. `cmd /c tools/breadcrumb.sh` gets misparsed, because cmd's switch scanner keeps hunting for more `/x`-shaped switches anywhere after `/c`, and a bare forward slash in an ordinary relative path reads as a second switch. The obvious fix — wrap the whole thing in quotes — *also* failed, for an even less obvious reason: cmd only preserves quotes under specific conditions, one of which requires whitespace *inside* the quoted string, and a bare path has none, so cmd silently stripped the quotes right back off. The actual fix — prefixing with `call ` — was verified empirically against real `cmd.exe` invocations, including confirming exit codes still propagated correctly, before it got trusted.
- **A stdin/stdout race.** A hook command that exits immediately without ever reading its input (an intentionally-failing test case, but a legitimate real-world shape too) could throw a broken-pipe exception that masked the actual, intended error message. Caught by an intermittently-failing test, fixed by treating a broken pipe on the write side as expected and letting the real exit-code check downstream produce the actual error — then verified by running the previously-flaky test five times in a row, since a single green run doesn't prove a timing bug is actually gone.

A real hook went straight into the dogfood site as proof, not just left as a unit test: a `curtain` script appending "— Curtain. —" to the bottom of the home and synopsis pages. The first version was almost too subtle to notice at a glance — a fair complaint — so it got a second hook alongside it: a PowerShell script computing a real per-page word count and reading-time estimate, inserted right under the page title where it can't be missed, chained together with `curtain` to prove multiple hooks compose in declared order. Both are still live in `workspace/` today, not reverted after verification.

## Act 9: "i gazed upon thine CSS" (Aug 18)

The last fix in this chronicle didn't come from a bug report or a design conversation — it came from a straight code review, delivered with its own sense of humor:

> "always reviewing your work, i gazed upon thine CSS. I like alot of it... but I noticed a negative, the base CSS seems to include some specific styling for widgets! but this seems to break are widget pattern, perhaps thine should have a seperate css file that can be imported in alongside the widgets for thine styling, what say you speak plainly and defend how thine mind reacts"

The critique held up completely under its own weight. `WidgetDiscovery` had always promised built-in and site-authored widgets were discovered *identically* — same folder scan, same filename lookup, no special-casing either direction. That symmetry was the entire point of the Round 2 widget redesign. But `downloads`/`slideshow`'s actual CSS had been hardcoded directly into the site's own `framework.css` since before that redesign even existed — a leftover from the very first "Skeleton added" commit, back when `framework.css` was split off from consoland's `style.css`, long before there was a real discoverable widget system to keep it symmetric with. Nobody had gone back and asked whether it still belonged there once that system existed. It didn't: a site author's own custom widget had nowhere to put CSS at all, while the two built-ins got free styling nobody else could get.

The fix reused machinery that already existed rather than inventing anything new: `WidgetDiscovery` was already generic over file pattern, so a third call with `"*.css"` cost nothing architecturally. `downloads.css`/`slideshow.css` got extracted out of `framework.css` verbatim (no rule changes — the extracted CSS references the same `--accent`/`--bg`/etc. tokens `framework.css` defines, which cascade globally regardless of which linked file references them), discovered and copied and linked exactly the way `.js` already was, via a new `{{widgetStyles}}` shell placeholder. Verified pixel-identical in a real browser afterward — the fix was entirely about *where* the CSS lived, never about what it said.

## Act 10: NavDepth, and a consoland assumption nobody had questioned in two days (Aug 18)

Asked what was left after the widget-CSS fix, the honest answer was "just Phase 4, `canary init`." That's not what came next. The next request landed with a sigh:

> "sigh there is something else that must change, and its pretty basic. we need to have a configurable NavDepth for going deeper, one level in when building a manifest was fine originally but that is a design choice for consoland, and is not a universal for canary, 'and wont work for the amazing interactive documentation canary will have where it serves up a doc site using the test server built in canary!'"

It held up immediately on inspection. `ManifestBuilder`'s nav-tree builder had been hardcoded to recurse exactly one level deep since the very first "all but canary init" commit — a direct, unexamined port of consoland's own `build-manifest.cs`, fine for a site that really was flat, silently wrong the moment a site wasn't. `ContentScanner` already found and built pages at *any* depth for real routing; the nav *menu* had just never been asked to look that deep. A page at `docs/guides/widgets.md` would build, get a real URL, and be completely invisible in nav — reachable only by a direct link, never surfaced.

The fix had two real halves, and only fixing one of them would have been a trap. The C# side was the straightforward part: a new `nav.depth` config field (default `1`, so every existing site's behavior stayed byte-for-byte identical; `<= 0` for unlimited), and `ManifestBuilder.BuildDirectoryNavItem` made properly recursive — a nested directory becomes a nav item the same way a top-level one always did, sorted alongside its sibling files in one dropdown. `.nav.json` auto-creation, which had the exact same "only ever looked one level deep" assumption baked in for the same unexamined reason, now reaches exactly as deep as the nav tree itself does.

The client side was the part that would have quietly broken everything if skipped: `nav.ts`'s renderer had never had a reason to be recursive, so it flattened every dropdown child straight into a plain `<a>` tag. A perfectly correct, deeply-nested `NavItem` tree coming out of the new C# code would have been silently truncated the moment it hit the browser — the exact same class of "the convention only got implemented on one side" bug that had already bitten this project twice (the widget-CSS split, the `spa` directory-index 404). Rewritten so a child with its own children renders as a nested flyout submenu instead, and `updateActiveNav` rewritten to walk up the DOM from wherever it actually matched, marking every ancestor level active — not just checking one level up, the way it always had.

Dogfooded immediately and for real, not as a synthetic test fixture: a new "Background" section went straight into `workspace/`, two genuine levels deep — `background/history/copyright-dispute.md`, `background/production/original-cast.md` — kept in permanently, same as every other feature this project has shipped. Driven in an actual browser: the nested flyout opened correctly on hover, and on the deepest page, all three ancestor levels — the top-level nav item, the nested subitem, the leaf link — lit up active together, in both `hybrid` and `static` modes. A stale copy of `workspace/css/framework.css` (never re-synced since the widget-CSS fix earlier that same day) got caught and fixed along the way, almost as an afterthought.

## Act 11: The chevron that took three tries (Aug 18)

The new flyout submenus needed some visual signal that a row expands further, so a small "❯" chevron went in next to any dropdown label with children. It shipped, got dogfooded, looked fine in a screenshot. Then:

> "well so long as you are updating the default template, I might say that the carrot you added being appended directly onto the text looks pretty bad"

What followed is worth recording in full, because the first two fixes both looked correct on inspection and neither one actually worked — a real, concrete lesson about verifying a claim against the DOM instead of a screenshot and a confident guess.

**Attempt 1:** the chevron was pinned to the far edge of its row via `justify-content: space-between`. Theory: a tightly auto-sized dropdown has no slack width for `space-between` to distribute, so the chevron sits wherever the content ends — right against the text. Fix: swap to a fixed `gap`. Declared fixed. It wasn't — "no not fixed, not verified," the very next message, after a hard refresh specifically to rule out caching. (One real, useful side effect: the dev server had been sending zero cache-control headers at all, a genuine gap for local dev regardless of whether it was the actual culprit here — fixed by sending `Cache-Control: no-store` on every response, so this entire class of confusion can't happen again going forward.)

**Attempt 2:** new theory — a CSS `::after` pseudo-element merges into the *same* anonymous flex item as the text it's attached to, since nothing separates them at the element level, so `gap` (which only inserts space *between* distinct flex items) had nothing to act on. Swapped the chevron to a real, separate `<span>`. Checked in a brand-new browser tab specifically to rule out any possible cache explanation. Still touching, confirmed by a tight zoomed screenshot.

**What actually fixed it:** giving up on reasoning about it and asking the page directly, via `getComputedStyle`. The real answer had nothing to do with either theory: `.nav-dropdown-label`'s own `display: flex` was never winning at all. A pre-existing, unrelated rule — `.nav-dropdown a { display: block; ... }` — has higher CSS specificity than a bare `.nav-dropdown-label` class selector, and had been silently overriding it the entire time. The element was never a flex container in the first place, in either attempt, which is exactly why neither fix could possibly have worked regardless of which one was "more correct" in isolation. Fixed by qualifying the selector to `.nav-dropdown .nav-dropdown-label`, specificity high enough to actually win. Verified this time by measuring the real rendered gap between the two elements' `getBoundingClientRect()`s — 8px, exactly the `0.5rem` the CSS asked for — not by looking at another screenshot and deciding it looked right.

## Act 12: The known bug, revisited — hash routing dies too (Aug 20)

Two days after the chevron fix, a status check turned up one loose thread `PLAN.md` had been carrying since Act 4: the "stale hash + real path mismatch" known bug, deliberately left unfixed at the time because it was rare — only hit on a bookmarked or shared mid-navigation URL. Asked whether any of the hashing machinery behind it was even load-bearing:

> "ok, on the known bug, is any of the hashing in there implemented, becuase my instinct is to just take it out"

It was real and fully implemented — `router.ts` was a genuine hash router, and `hybrid-router.ts`'s whole warm-navigation mechanism was built on top of it. But the instinct held up under inspection: hash routing had only ever been structurally necessary for a *pure* SPA with no real per-route files to route to — GitHub Pages can't rewrite server-side, so the hash was the only way to route client-side at all (see Act 0). `hybrid` mode never had that constraint. Every route already gets a real prerendered file at its real path; the hash had simply been carried over unexamined when the router got ported from consoland's original design, the same "convention only reimplemented on one side, and only partly examined" pattern that had already bitten this project three separate times.

The fix: `router.ts` rewritten around `pushState`/`popstate` instead of `hashchange` — intercept a click on a same-origin `<a href>`, `preventDefault` the browser's own navigation, push the real path, then run the exact same fragment-fetch-and-splice mechanism that already existed. The known bug disappears by construction, not by patching: there's no second, hash-shaped piece of state left to disagree with the served path. A pleasant side effect got noticed before the work even started:

> "I like too that it would mean we dont have the f-ed urls like /games/#/games/tesselate"

And a real design question got asked and answered before any code changed — whether losing the hash also meant losing the instant, no-reload feel warm navigation had always had:

> "can real path navigation, once on page still give us that SPA style clean load without page flashes."

It does, and it's the standard mechanism behind virtually every modern client router, not a compromise: `preventDefault` stops the browser's native navigation before it ever starts, `pushState` updates the address bar with zero navigation, and the same DOM-swap logic that already existed handles the rest. One real bonus fell out of making the router generic over "any internal link click" instead of only ever intercepting nav's own hash-shaped `href`s: in-content markdown links, which used to fall through to a full page reload because they were already real hrefs the old hash router had no reason to touch, now get the same instant swap nav always had — a UX inconsistency this fix incidentally removed rather than one it had to specifically design around.

Verified live in a browser, the actual bug scenario and all: a cold hard-refresh directly on a deep bookmarked URL (`/characters/frederic/`) now shows the right content *and* the right nav highlighting immediately, because there's no hash left to have ever disagreed with it in the first place.

## Act 13: "an edge-case monster" — checksumming dies, hooks learn where they are (Aug 20)

The same status check turned into a design conversation about a feature the user had wanted for a while: giving hooks enough context to do *mass* modification across a site, not just transform one page in isolation.

> "Im thinking about adding Route-Path, and the navigation manifest, so lets say I wanted to write a tool that adds something to every navigable page under games, it would make doing that easy. One big thing with tool chain is mass programatic page modifications."

That, on its own, would have been a small, contained addition — two environment variables on a hook's process. But designing it surfaced a real correctness gap: once a hook can read the manifest, its output can depend on content *outside* its own page (a sibling joining or leaving `games/`), and the incremental-build cache had no way to know that — the exact "the gate doesn't track everything the hook can see" bug class that had already been hit twice before (widget files, then hook scripts themselves, both fixed back in Act 8). Flagging that gap turned into the real conversation of the day. The user's actual read on checksum-gating, once it was back on the table:

> "lets talk about the canary serve thing, couldnt we on file change still just ony run the one updated file through the toolchain again?"

and, more bluntly, on the whole mechanism it would take to keep patching:

> "I think this is solvable without checksums."

and the verdict on checksum-gating itself, once alternatives were actually on the table:

> "im gonna drop checksumming entirely, at least for the time being. Its proving to be an edge-case monster, the compile time speedup probably isint worth the reliability hit"

It was a fair read of its own history: missed widget files, missed hook scripts, the `cmd.exe` quoting fiasco, the `HookRunner` stdin race, a test-fixture gap that briefly looked like a real regression — checksum-gating had needed a bug-fix pass practically every time it got touched. But pulling on the thread of *why* it existed at all — re-reading `PLAN.md`'s own original rationale — showed it had actually been solving two different problems bundled into one fragile mechanism: keeping `canary serve`'s watch-loop fast, and keeping a committed `output.dir`'s git diffs small. Split apart, neither one needs a cache:

- **Dev-loop speed** is exactly what the user had already half-proposed: since `FileSystemWatcher` already knows which file changed, `SiteWatcher` now accumulates that during its debounce window and hands it to `SiteBuilder`, which renders *only* the matching route when the change set is unambiguous (a plain edit to one existing page) and falls back to a full rebuild for anything structural — a page added or removed, a widget/hook/theme/config edit. No invalidation-tracking anywhere; the filesystem event just says what changed, directly.
- **Clean diffs** turned out not to need caching either, once the deterministic-rendering property was actually used instead of worked around: render every page fresh, always, then compare the freshly-built HTML against whatever's already on disk and skip the write only when it's identical. An unchanged page produces identical bytes by definition, so this gets the exact same "small, meaningful diffs" property the checksum comment existed for — by direct comparison against reality, instead of by trying to track every input that could make a cached result stale.

Both mechanisms are structurally incapable of the bug class that kept recurring, because neither one caches anything to begin with. `PageBuilder`'s checksum comment, its two regexes, the `extraChecksumSeed`/`widgetChecksumSeed` threading, and `HookRunner.ChecksumSeed` all came out in one pass — along with the `{{checksum}}` template placeholder, dropped with no backward-compatibility shim, on the honest grounds that pre-release software doesn't need one yet.

A short, sharp self-review pass happened before any of it got built — four critiques raised, three accepted outright and folded into the plan (a `HookContext` record instead of three same-typed bare-string parameters that would've been easy to transpose; a build-twice-in-a-row idempotency test to replace coverage that would otherwise have quietly disappeared; landing the checksum removal and the hook env-vars as two separate, independently-verified passes rather than touching `HookRunner`'s signature twice at once), one waved off in three words:

> "4. we are still in pre-release, so I appreciate the compatibility advice but I dont think its necessary"

`CANARY_ROUTE_PATH` and `CANARY_MANIFEST_PATH` landed once the removal was done and green — delivered as environment variables specifically to avoid reopening the `cmd.exe`-quoting minefield `HookRunner` had already fought and won once (Act 8) with a second CLI argument to get right. `CANARY_ROUTE_PATH` uses the bare nav-tree convention (`""` for the site root), not the URL-style convention `ContentScanner`/the sitemap use — confirmed, not assumed, by actually re-checking both conventions against this session's own router rewrite before committing to the choice, since it directly matches `manifest.json`'s own `path` fields with zero translation required.

Verified live against the dogfood site: a bare rebuild with nothing changed reports `written=0, unchanged=11`; editing one page's markdown while `canary serve` was running triggers a rebuild that processes exactly that one route, not all eleven; editing a theme stylesheet correctly falls back to a full rebuild; and a temporary debug hook confirmed a nested page (`characters/frederic`) receives its own correct route path and a manifest path pointing at a real, current, on-disk `manifest.json` — the actual mass-modification scenario the whole feature was built for, working end to end.

## Act 15: "I guess its time to build the last piece huh" — canary.json, and a decision nobody could find (Aug 21)

Phase 4 — `canary init` — was the one item left on the original phase list, unstarted since Phase 0. The request to build it came casually: *"neat, i guess its time to build the last piece hih."* What followed instead of straight-to-code was a full plan-mode round trip, because `canary init` was already the one part of `PLAN.md` explicitly flagged as having real, undecided questions in it.

**Clarifying first.** Three concrete calls got made before any code: `canary init` takes an optional positional target directory (`canary init [path]`, default `.`), not just the working directory; the built-in `downloads`/`slideshow` widgets get **always overwritten** on every init run, not copied once and left alone (simpler, and `preferBuiltIn` already exists as the escape hatch for anyone who wants their edits to stick); and — the one that went sideways — what should happen when `canary.json` already exists in the target directory.

**The decision that wasn't in the record.** Asked to confirm the overwrite-safety behavior, the user's answer was *"we talked about this, adding a flag to config.json that prevents overrite without a --force argument, this should all be in the plan already."* It wasn't. A full search — every commit in `PLAN.md`'s git history via `git log -p -S`, every other markdown file in the repo, all of memory — turned up nothing resembling a `--force`/init-guard decision anywhere, only the same unresolved "open question" that had existed unchanged since the very first `PLAN.md` commit on day one. Rather than keep insisting or silently inventing something plausible, the gap got reported plainly, and the user made the call explicitly, on the spot: *"Decide it now."* The design landed on an explicit `initialized: true` marker written into `canary.json` itself by a successful `canary init`, checked by future runs — chosen specifically because it's a self-documenting flag `canary init` itself controls, rather than inferring "already a project" from the file's mere existence, the same "explicit beats implicit" instinct behind the `!url` widget tag from Act 3.

**The rename, done first on request.** Before any of the init logic got written, a second, separate ask arrived: rename `config.json` to `canary.json` everywhere, "so we know its a config file by site for the canary framework" — the same reasoning `package.json`/`tsconfig.json` lean on. Handled as its own pass ahead of the init work: `Program.cs`'s default path, error/comment text in `ToolchainRunner`/`SiteBuilder`, `WIDGETS.md`, seven spots in `PLAN.md`, a test literal, and a `git mv workspace/config.json workspace/canary.json` to keep the file's history intact. `devJournal.md` was deliberately left alone — `config.json` really was the name at the time each earlier Act happened, and rewriting history to match the present would make the record less honest, not more.

**Implementation.** A new `Canary.Core.Init` namespace — `SiteInitializer` (no `Console` I/O, same split `SiteBuilder`/`ConfigLoader` already use), `InitOptions`, `InitResult` — scaffolds `canary.json` (hand-built as a `JsonObject`, not `JsonSerializer.Serialize`, to keep camelCase keys consistent with every hand-authored config in the repo), `shell.html`/`css/framework.css` from `templates/default/`, a brand-new generic `templates/default/css/theme.css` starter (didn't exist before — only `workspace/`'s site-specific theme did), and `<content.root>/index.md`. The widgets and theme/shell files are always overwritten once execution reaches that point; `content/index.md` is created only if missing and never touched again, even with `--force` — real content, not framework scaffold. `Program.cs` grew the actual `init` command: positional path parsing, a new `HasFlag` helper, a `ResolveRuntimeDistDir` generalized into `ResolveRepoSubdir` (shared by the runtime-dist and templates-dir lookups instead of two copies of the same walk-up-8-levels loop), and a full interactive prompt sequence.

**A real bug, found the way this project always finds them.** First live test: `dotnet run --project src/Canary -- init workspace` against the real, already-initialized dogfood project — and it hung. Not a timeout, an actual infinite loop: `RunInit` ran the entire eight-question interactive prompt sequence *before* ever checking whether `canary.json` already existed, so with no stdin available (`Console.ReadLine()` returning `null` on EOF) `PromptRequired`'s reprompt loop span forever, dumping "(required)" as fast as the process could write it — a 32MB output file before the command got killed. Fixed two ways: `SiteInitializer.CheckAlreadyInitialized` got pulled out as its own public method so the CLI can check it *before* prompting at all (no point asking eight questions just to refuse at the end), and `PromptRequired` itself learned to treat a `null` read as a fatal, immediately-reported error instead of an empty string to keep looping on — the actual robustness gap, independent of the ordering bug that first exposed it.

Verified live, not just in tests: `canary init workspace` now refuses instantly and correctly (`workspace/canary.json` already exists, wasn't created by `canary init`, no `--force`); a fresh scratch project scaffolded via `--config workspace/canary.json` inherited its core values (site name, `nav.depth: 2`) while getting its own theme/tools; a second scratch project scaffolded fully interactively via piped stdin came out identical in shape; both built cleanly end-to-end through the real `canary build` pipeline. 144 tests passing, up from 138.

## Act 16: "chances are they will have generated different ports" (Aug 21)

`canary serve`'s port had been a hardcoded `8080` since Phase 2 (Act 3-era). Asked in passing whether that was still a good idea, the objection was concrete: *"devs run alot of silly littly webservers on local ports for different projects so defaulting to 8080 seems to invite accidental collisions."*

**First pass, and a real misread.** The fix that shipped first was a new `ServeConfig.Port` field, defaulting to a single fixed, deliberately uncommon value — `6913`, picked to avoid the actual well-known local-dev defaults (`3000`/`3001` Node/React, `4200` Angular, `5000`/`5001` Flask/Kestrel, `5173` Vite, `8000` Django, `8080`/`8081`, `8888` Jupyter, `9000` PHP-FPM/SonarQube) — wired through `canary serve` and prompted for during `canary init`. It solved "don't collide with someone else's Node server" but missed the actual point. The correction: *"you miss understand, I mean that init should generate one on the fly, so if you have 2 canary sites you are working on, chances are they will have generated different ports."* A fixed constant, however uncommon, still collides with itself the moment two Canary projects both exist.

**The real fix.** `Program.GenerateRandomServePort()` picks a fresh value in `[6500, 7000)` — a sub-range chosen so `ServeConfig`'s own static `6913` fallback (for a hand-written `canary.json` that skips `serve` entirely) sits inside the same pool, one member of it rather than a separate special case. `canary init` calls it fresh on every run: shown as the interactive prompt's overridable default, and applied silently in `--config` mode, where the port joins theme paths and the tools registry in the category of things a scaffold never copies from its source — copying a source's port would have defeated the entire point, recreating the exact collision the feature exists to prevent.

Verified live: two scratch projects both scaffolded from `--config workspace/canary.json`, back to back, came out with `6772` and `6978` respectively; an interactive run's prompt showed `Serve port [6894]` — a different value every time, not the same number printed twice.

## Act 17: an example tool that teaches by demonstrating, not by describing (Aug 21)

Two related, back-to-back requests: first, that `canary init` should scaffold a `tools/` directory with "an example do nothing tool, written in C#, that basically reads the input stream line by line and outputs it to the output stream" — a genuine starting point, not a placeholder. `templates/default/tools/example.cs` is exactly that: seven lines, no `.csproj`, run via `dotnet run tools/example.cs`, matching `curtain.cs`'s own file-based-app shape from Act 14. `SiteInitializer` copies it alongside `shell.html`/`css/*` (always overwritten, same treatment) and registers it in the generated `canary.json`'s `tools` dict — `"example": "dotnet run tools/example.cs"` — but deliberately doesn't apply it anywhere; no `.toolchain.json` references it on a fresh project, matching the "registration and application are separate, application is never automatic" design from Act 6.

The follow-up landed before the first one was even fully wrapped up: *"the tool generated should also load the other arguments as variables."* Not CLI arguments — a toolchain tool never receives any (the whole contract is stdin plus two environment variables, `CANARY_ROUTE_PATH`/`CANARY_MANIFEST_PATH`, from Act 13). `example.cs` grew two lines reading both into local variables and writing them to `stderr` — deliberately stderr, not stdout, since `ToolchainRunner` silently discards a successful command's stderr and only surfaces it inside a failure's exception message, so the demonstration doesn't compromise the tool's own "do nothing to the markdown" promise. Verified by setting both env vars directly and piping real input through the script standalone (stderr showed the proof line, stdout passed the input through byte-for-byte), and by applying `"example"` to a scratch project's real `content/.toolchain.json` and confirming `canary build` still completes cleanly with unmodified output.

## Act 18: the last feature, and a bug that had nothing to do with Canary (Aug 21)

*"Ok, well I guess its done then with version 1 except 1 feature."* The one left: a publish step. The framing came with its own constraint built in — *"not ncessasarily [git add/commit/push]... because people will host sites in different ways so we want a simple, run this, for canary publish."* No deploy-target abstraction, no git-specific or FTP-specific mechanism — one arbitrary command, same anti-abstraction stance the toolchain has always taken.

**Design.** `canary.json` gets a bare top-level `"publish"` string, not a nested object — there's nothing to configure beyond the command itself. `canary publish` always builds first (publishing stale output would be worse than refusing outright), then runs the command with exactly one environment variable, `CANARY_OUTPUT_DIR` — the absolute `output.dir` path, so a publish command never has to hardcode or duplicate a directory name that's already declared in config. No `CANARY_ROUTE_PATH`/`CANARY_MANIFEST_PATH` here; publishing is a whole-site action, not a per-page one. `ToolchainRunner`'s hard-won `cmd.exe`-quoting fix (the two-bugs-deep `call`-prefix trick from Act 8) got pulled out into a new shared `Canary.Core.Shell.ShellCommand.Resolve`, used by both `ToolchainRunner` and the new `Canary.Core.Publish.PublishRunner` — a toolchain tool and a publish command are both "run this string as a shell command," so there was no reason to re-derive the same fix twice.

**Bug one: "live output" that couldn't actually start.** The first version of `PublishRunner` deliberately didn't redirect the child process's stdout/stderr at all — the whole point of a publish command is watching `git push`'s progress happen, not getting a buffered wall of text after the fact, so inheriting the console directly seemed like the obvious choice. It failed outright: every test threw `exit code 1` before the script even ran. Isolated with a standalone `dotnet run` repro outside the test suite, the cause turned out to be exactly what it looked like — inheriting console handles doesn't work in a non-interactive host with nothing real attached to inherit. Fixed by redirecting the streams after all, but forwarding each line to `Console.Out`/`Console.Error` live as it arrives (`OutputDataReceived`/`ErrorDataReceived` plus `BeginOutputReadLine`/`BeginErrorReadLine`) instead of buffering to a string — genuinely the more robust choice, not just a workaround, since it doesn't depend on what kind of console (if any) the parent process happens to have.

**Bug two: a landmine that had nothing to do with .NET at all.** Even after that fix, the exact same three tests kept failing, now with a stranger error: `'publish.cmd' is not recognized as an internal or external command`, for a file that was verifiably sitting right there in the working directory. Debugging this one meant stepping outside the test suite entirely — a series of throwaway `dotnet run` scratch scripts, each isolating one variable, eventually showing that `call publish.cmd` (a bare filename) failed while `call tools/marker.cmd` and `call ./publish.cmd` (anything with a path separator) both succeeded, using the identical working directory in every case. That pointed at Windows' `NoDefaultCurrentDirectoryInExePath` security hardening setting — confirmed present in this environment with a one-line `cmd.exe /c "set NoDefaultCurrentDirectoryInExePath"` check. When set, it disables implicit current-directory search for a bare command name with no path separator; a path *with* a separator bypasses that search algorithm entirely, which is exactly the split observed. A real, sometimes IT-policy-enforced setting, not an artifact of this particular sandbox.

Deliberately **not** patched in `ShellCommand.Resolve` itself: there's no way to tell "a bare name meaning a local file" apart from "a bare name meaning a PATH-resolved executable" (`dotnet`, `git`, `powershell` are exactly this shape) without checking the filesystem, and `Resolve` isn't even given a working directory to check against. Documented instead, in `ShellCommand`'s own comment and in `PLAN.md`: a local script command should always carry an explicit path (`tools/foo.cmd`, `./foo.cmd`), never a bare filename — which every command Canary itself ships already does. The test fixtures got moved into a `publish/` subdirectory specifically so they'd double as proof the guidance actually works, not just a description of it.

This also quietly closed out Phase 6, the long-parked "remote push (FTP/SFTP), later/optional" placeholder from the very first `PLAN.md`: a site author gets that today by writing their own FTP/SFTP/rsync one-liner as `publish`, no Canary-side client ever needed. It's also a real, explicit revision of a stance `PLAN.md` staked out at Phase 0 — *"Canary shouldn't be auto-committing/pushing"* — reconciled rather than quietly contradicted: still true in spirit, since Canary still has no opinion about deploy mechanics and never runs anything the site author didn't write; just no longer true in the narrow, literal sense, since it can now push, but only because it was told to.

Verified: 148/148 tests (up from 144), including the new `PublishRunnerTests`; live end-to-end against a scratch project (`canary publish` built first, streamed `echo %CANARY_OUTPUT_DIR%`'s own output live, resolved the real absolute `docs/` path, exited `0`) and against `workspace/` (no `publish` configured, failed with a clear message instead of doing nothing).

## Act 19: the documentation dogfoods itself (Aug 21)

*"Isint that just fucking clever"* — the pitch was for Canary's own user-facing documentation to live in two places (a `docs/` directory for GitHub, and eventually alongside a real install) and to itself be a Canary site, built by the same `canary build` a consumer would run. Planning came first, in chat rather than code: a survey of the existing config/manifest/toolchain/widget machinery to write an accurate content outline, then two genuinely open questions put to the user directly rather than assumed — what "lives in the install directory" should mean before any packaging exists to design around, and where the site's own source should sit in the repo. Both landed on the lighter-weight option: ship it next to the built exe *once something actually reads it from there* (nothing did yet), and a new top-level `docsite/`, mirroring `workspace/`'s own layout rather than nesting inside it.

*"Roll out the whole shibang"* was the go-ahead. `docsite/` scaffolded by hand rather than through `canary init` (the schema was already fully known from reading `CanaryConfig` directly) — `canary.json` pointing `output.dir` at `../docs`, a copy of the generic `shell.html`/`framework.css`, and a new canary-yellow `theme.css` supplying `pre`/`code` styling the base framework deliberately doesn't ship. Fourteen content pages across Home, Getting Started, Guide, and Reference, written against the real CLI/config behavior (re-confirmed from `Program.cs` rather than assumed) rather than the plan's own prose, since `PLAN.md`'s dated decision-log voice isn't the right one for a docs reader.

**A real markdown-renderer constraint surfaced immediately, not hypothetically.** `MarkdownRenderer.FenceRegex` has no concept of backtick-count escaping the way CommonMark does — a widget name as a fence's info string always dispatches to that widget, so there was no way to show the `downloads`/`slideshow` fence syntax itself as literal example text; writing it just ran the widget instead of displaying it. First pass worked around this by describing each widget's fields in prose/lists instead — noted honestly as a workaround, not a real fix, in both the doc content and `PLAN.md`.

**A second discovery, purely from actually building the thing rather than planning it**: `canary.json` needed an explicit `theme` block after all — omitting it (following `workspace/canary.json`'s own terse style) failed the very first real build with `theme.shell is required`, a validation `SiteBuilder` enforces that isn't visible from `ConfigLoader`'s own validation alone. Fixed by adding the block; caught in seconds because the very next step was always running the real `canary build`, not just writing content and assuming it would work.

Also fixed along the way, not left for later: `.gitignore`'s blanket `docs/` rule (originally written to keep every site's generated build output out of git) would have silently swallowed this site's own output too, defeating the entire point of shipping it to GitHub. A `!/docs/` carve-out fixed it for the repo root specifically, while checking (and, in `PLAN.md`, correcting) an adjacent stale claim that `workspace/docs/` was already tracked — it wasn't, and never had been; the earlier note describing it that way was aspirational prose that had drifted from what `.gitignore` actually did.

Verified past "the build succeeded": served locally and clicked through in a real browser via `claude-in-chrome` — nav dropdowns, active-page highlighting, code-chip styling, the whole rendered chrome — not just a green build log. 148/148 tests still passing (nothing in `src/` changed this Act, only content and config).

## Act 20: a widget for showing widget syntax, not describing it (Aug 21)

The workaround from Act 19 didn't sit well: *"why dont you build a widget for displaying widget syntax in a code window"* — build the actual fix, not the polite description of the limitation. The fence-dispatch problem was real and unavoidable at the markdown-renderer level, but a widget's own YAML body is never re-parsed for fence boundaries — it's just data handed to a template. So a third built-in widget, `code` (`runtime/widgets/code.{html,css}`, no `.js`, purely static), takes a `lines` list and renders it back out as an escaped, verbatim `<pre><code>` block. Wrapping an example one line at a time inside a `code` fence sidesteps the whole problem: the *outer* fence's info string is `code`, so it renders instead of running, and a literal `` ``` `` inside the YAML body is just text, never re-scanned as a real fence boundary.

Getting there required actually reading, not assuming, two hand-rolled parsers' real constraints first: `YamlParser` has no multi-line block-scalar support, so a multi-line example has to be one list entry per line; and `MustacheTemplate` has no `{{.}}` self-reference for a bare scalar inside a section, so each line had to be a one-field `{ text: "..." }` map, not a bare string in a list, or the template would have had nothing to look up at all.

**A real bug found by rendering the widget's own canonical example, not by inspecting it.** The first version of that example tried backslash-escaping a literal double quote inside a double-quoted YAML scalar (`"...\"...\""`) — natural muscle memory from nearly every other language's string syntax, and wrong here: `YamlParser.ParseScalarText` strips a scalar's matching outer quote pair but never unescapes anything inside one, so the output came out as literal `\&quot;My File\&quot;` instead of a clean quoted string. Caught by actually building a scratch test page and reading the rendered HTML, not by reasoning about the parser on paper. Fixed by using single quotes as the line's own delimiter whenever it contains a literal double quote — documented directly in `code.html`'s own doc comment (where the next author writing an example will actually see it) and in the finished `guide/widgets.md`, not just in `PLAN.md`.

With `code` working, `guide/widgets.md` got rewritten to use it for real: the `downloads`/`slideshow` examples now show actual, correct fence syntax rendered as text, not the earlier prose-only field descriptions. `reference/faq.md`'s entry on the same question changed from "here's why you can't" to "here's how" accordingly. Verified: a scratch test page through the real pipeline, checked in a browser at each step of fixing the quoting bug (broken, then fixed), and the full guide/widgets.md page reviewed rendered end to end; 148/148 tests still green, since none of this touched compiled C# behavior — the widget is pure discovered `.html`/`.css`, the same "no widget-specific code anywhere" property every built-in widget has had since Act 3's redesign.

## Act 21: `canary docs`, and a lock file for a command that only makes sense running once (Aug 21)

*"Onto the canary docs command, which opens this website on a random unused port between 9000-9999."* Built as a genuine consumer of `docs/`, not just a static preview: `RunDocs` resolves the repo root's `docs/` via the same `ResolveRepoSubdir` walk-up `templates/default`/`runtime/dist` already use (already proven, in Act 19, to work from a from-source checkout with zero copying), picks a port via a new `FindUnusedPort` — a bind-then-release `TcpListener` probe, genuinely checking availability rather than just avoiding a well-known range the way `canary init`'s serve-port default does — and best-effort launches the system default browser (`ProcessStartInfo`/`UseShellExecute` on Windows, `open`/`xdg-open` elsewhere, swallowed on failure since the server and its printed URL are already there regardless). This closed a loop from Act 19's own plan: shipping `docs/` "with the install" had been explicitly deferred there for having no real consumer yet; now there was one.

The very next message pushed it further: *"canary docs should when opening make a little flag file in appdata with the process id and the port, and clean that up on closing, when run again it should see if that previous process is still running and if it is just say, docs already open at localhost:\<port number\>... there should be a --force option to try and close the old version and start a new one (in case of a hung process)."* Implemented as a small JSON lock file (`{pid, port}`) at `%APPDATA%/Canary/docs.lock.json`, `Environment.SpecialFolder.ApplicationData` rather than a hardcoded Windows path, matching the project's stated (if still Windows-only-verified) cross-platform intent elsewhere. A second `canary docs` while the recorded pid is still alive just prints where the first one is and exits; `--force` kills it (`Process.Kill()` plus a bounded `WaitForExit`, explicitly best-effort — "try to close," per the user's own framing, not guaranteed) and starts fresh. The case that needed no flag at all: a lock file whose pid has already died on its own — a crash, not a clean shutdown — gets silently cleaned up and the command just starts normally, since only a genuinely still-alive-but-stuck process needs forcing away.

Verified the whole state machine live, not just read back: a fresh start wrote a lock file matching the real pid; a second invocation correctly refused with the right port; `--force` correctly killed the first and started a second on a new port with its own fresh lock; a hard `Stop-Process -Force` against that second instance (simulating a real crash, not a graceful exit) left its lock file behind exactly as expected, proving the scenario `--force` exists for is real; and a plain `canary docs` run right after that, with no `--force`, silently detected the dead pid and started cleanly with no error and no false "already open" message. 148/148 tests still passing throughout.

## Where 0.1.0 landed

Every phase from the original plan is done. Two render modes, not three. A widget system that took two real rounds to get right, and is now symmetric across all three of its file types. A content toolchain (built as "hooks," renamed to the name the user actually used for it from the start — see Act 14) designed carefully enough in conversation that its implementation surfaced only real, fixable bugs — never a design flaw, three times over now (building it, giving it more context, teaching it via a scaffolded example). A nav tree that finally recurses as deep as a site actually needs it to. A client router keyed off real paths instead of a hash fragment, with no known bugs left over from the switch. No incremental-build cache anywhere in the system — full re-render, every page, every time, with the two properties that cache used to provide (a fast `canary serve` loop, clean `output.dir` diffs) recovered by simpler, harder-to-get-wrong means instead. `canary init` scaffolds a real, working project — config, theme, starter content, widgets, an example tool, a collision-resistant random dev port — in either of two modes, and `canary publish` closes the loop with one arbitrary, site-author-owned deploy command, no built-in deploy-target abstraction anywhere in sight. 148 tests, up from 8 on day one. A dogfood site that's accumulated real, working, live examples of every feature as it landed, rather than a pile of synthetic test fixtures nobody ever actually looks at — and, as of Act 14, tracked in the repo itself instead of gitignored, because it stopped being disposable a long time before anyone updated the comment saying it was. As of Act 18 the whole v1 feature set is implemented, dogfooded, and tested, but still sitting uncommitted in the working tree — the one thing every prior Act in this document could take for granted (a real commit to point at) that this stretch of work can't yet. Acts 19–21 added a second dogfood site on top of `workspace/`'s — this one Canary's own real user-facing documentation rather than a fictional example — a third built-in widget born directly from a limitation that site's own construction exposed, and a `canary docs` command with real single-instance process/lock-file handling, still all uncommitted alongside everything from Act 18.

A few things kept showing up, project-wide, often enough to call them the actual throughline of 0.1.0:

- **Real bugs came from actually running things, almost never from reading the code.** The slideshow URL bug, the doc-comment self-collision, the runaway file watcher, the cold-load nav-highlight bug, the spa directory-index 404, the `cmd.exe` quoting fiasco, the stdin race, the nav-depth chevron, the `canary init` EOF prompt loop, `PublishRunner`'s console-inheritance failure, the `NoDefaultCurrentDirectoryInExePath` landmine, `docsite/canary.json`'s missing `theme` block, the `YamlParser` backslash-escape bug found only by rendering the `code` widget's own canonical example — every one of these was invisible on paper and obvious the moment something actually executed, in a browser or a real shell, against real input. The `NoDefaultCurrentDirectoryInExePath` one wasn't even a Canary bug — a real Windows security setting nobody involved had reason to suspect until a script that should have worked simply didn't.
- **When memory and the record disagree, say so and decide fresh rather than guess which one's right.** Asked to build `canary init`'s overwrite-safety behavior, the user was certain a `--force`-flag decision had already been made and documented; a full search of `PLAN.md`'s entire git history, every other doc, and memory found nothing. The honest move wasn't to quietly invent a plausible-sounding history to match the claim, or to keep re-litigating whether it existed — it was reporting the gap plainly and letting the user make the call again, on the spot, as a fresh decision.
- **Explicit beat implicit, every time it came up.** The `!url` tag over guessing by field name. Non-cascading hooks over inheritance. A separate `.hooks.json` over folding into `.nav.json`. A `HookContext` record over three bare strings that happened to share a type. Each of these cost something (more typing, more repetition, more files, more ceremony) in exchange for never having to trace up a tree, guess at what the system inferred, or misalign a positional argument.
- **Fix it once, not twice.** The widget-checksum bug sat logged and unfixed for a full day specifically so it could be fixed together with the hooks-checksum gap that hadn't been built yet, rather than touching the same fragile code twice. When that same class of gap threatened to recur a third time — the manifest-dependent-hook staleness risk in Act 13 — the answer wasn't a third patch, it was removing the thing that kept needing patching.
- **A mechanism that keeps needing bug fixes is a signal, not bad luck.** Checksum-gating got fixed correctly, repeatedly, by real engineering effort — and it *still* kept finding new edge cases, because embedding derived state in output and trying to track every input that could invalidate it is a genuinely hard problem to get exhaustively right. The eventual fix wasn't a better cache; it was noticing the two things the cache bought could each be had directly, with nothing to invalidate in the first place.
- **The dogfood site is not a demo.** It's a real, accumulating, live proof — every render mode, every widget, every hook, deep nav, real paths, all still there, all still working, because leaving them in and rebuilding them is cheaper than pretending they were never real in the first place.
- **"It looks right" is not verification.** The chevron got "fixed" twice, confidently, before it actually was — both times because a plausible theory plus a glance at the result stood in for actually checking. The pattern that finally worked wasn't a better guess, it was asking the DOM directly (`getComputedStyle`, `getBoundingClientRect`) instead of trusting a screenshot and a story about why it should be right. The same discipline showed up again in Act 13: "written=0, unchanged=11" is a claim a build makes about itself, and it only means something because it got checked against an actual second build, an actual running `canary serve`, and an actual hook's actual output — not because the code looked correct on the page.

## Act 22: finishing the 0.2.0 list, and cmd.exe's third bug (Aug 24)

Work resumed against `plan-0-2-0.md`'s open items, starting small: `canary widgets`/`canary widget <name>` — two commands for one concept, a naming trap where nothing about either name signals which one takes an argument — collapsed into one `canary widgets [<name>]`, reusing the exact optional-positional-arg convention `canary init`'s own `targetDir` parsing already established. No alias kept for the old singular form, same "pre-release doesn't need a compatibility shim" stance the project settled on back in Act 15.

The bigger item: `plan-0-2-0.md`'s "persistent toolchain-tool workers" experiment, narrowed during its own writing to a smaller, near-term fix — let a `tools` registry entry optionally point at a `.cs` source, add a `canary tools build` command that precompiles it once via `dotnet publish`, and have `canary build` warn (never block) if the source has drifted ahead of the compiled binary. The plan doc's own reasoning for *why not* an automatic rebuild-if-stale cache leaned directly on Act 13's checksum-gating post-mortem: an "edge-case monster" once, always a candidate to become one again — so the fix stayed advisory-only, never authoritative, on purpose.

**Decided in real conversation, not assumed:** which publish mode to target. Framework-dependent and self-contained-but-still-JIT'd builds were both ruled out for the same reason — they'd still pay the CLR startup cost on every launch, meaning they wouldn't actually fix the problem the feature exists for. Native AOT was the only mode that delivered on the goal, but the first live test of it failed outright — `dotnet publish curtain.cs -p:PublishAot=true` errored with `'vswhere.exe' is not recognized`, and the honest first read was that AOT publishing was broken in this environment. The user's reaction cut straight through that:

> "we are gonna use AOT but i dont get WHY you think it wont work on this machine, canary is built with AOT and IT was built on this machine"

Fair, and correct — Canary's own `PublishAot=true` build had clearly worked before. The actual cause turned out to be narrower and less interesting than "broken toolchain": `vswhere.exe` genuinely exists on disk, just not on the PATH of the specific shell sessions being used to test from. Adding its directory to PATH fixed the publish immediately, confirmed with the exact explicit invocation the user asked to see run (`dotnet publish -r <rid> -p:PublishAot=true`) rather than just being told it now worked.

**The AOT build's own side effects got caught the same way, not assumed away.** A stray multi-megabyte `.pdb` sitting next to a compiled tool's ~1MB `.exe` turned into its own short back-and-forth (`-p:DebugType=none` fixed it, confirmed by a from-scratch build after clearing the SDK's incremental-build cache, since the first "fix" attempt actually just left a stale `.pdb` from an earlier run sitting there unnoticed). And `dotnet publish` naming its output after the *source* file's own basename, not whatever filename the `command` field asked for, would have been a real, silent footgun — a `canary.jsonc` author writing a mismatched `command` path would build successfully and then have `canary build` report "missing binary" forever. Fixed with `-p:AssemblyName=<basename of command>`, which decouples the two names entirely; confirmed by actually renaming one and rebuilding, not by reading MSBuild documentation and trusting it.

**Then a real bug showed up the first time the feature actually ran end to end, not in any unit test.** `canary build` failed trying to run the freshly precompiled tool, with `'tools' is not recognized as an internal or external command` — the exact symptom `ShellCommand.cs`'s own comment already describes as the *unfixed* case from Act 8. `call`'s batch-file handling tolerates an unquoted forward-slash path; a precompiled tool's `command` is never a batch file, it's a bare `.exe`, and that shape falls through to a plain external-command dispatch where the same switch-scanning misparse resurfaces. Isolated the same way Act 8 isolated it the first time — a series of throwaway `cmd.exe` invocations outside the test suite, one variable changed at a time, confirming that quoting *only the first token* (the program itself, never the arguments after it) was the one fix that didn't break the multi-word commands the existing test suite already covered. `Resolve()`'s own doc comment, revised on the spot: "cmd.exe's own command-line quoting is famously two bugs deep" became "two bugs deep, and it turns out to be three." Locked in with a fast, string-only unit test on `Resolve()`'s literal output, plus a real regression case that runs a freshly-compiled tool through the actual `ToolchainRunner`/`cmd.exe` path — the gap that let the bug ship unnoticed the first time, since the tool-build tests up to that point only ever invoked the compiled `.exe` directly via `Process.Start`, never through `ShellCommand` at all.

Verified live against the real dogfood site: `workspace/canary.jsonc`'s `curtain` entry converted from `"dotnet run tools/curtain.cs"` to the precompiled `{ command, source }` form for real, `canary tools build curtain` producing a working `tools/bin/curtain.exe`, and a full `canary build` chaining it correctly alongside the untouched `reading-time` plain-string entry — both tools' effects showing up in the rendered page. 166 tests passing, up from 148.

## Act 23: a gitignore, a rename nobody planned going in, and a bug the user caught in about ten seconds (Aug 24–25)

Verifying the tools-build feature against a real scaffolded project surfaced a gap nobody had gone looking for: `workspace/`'s compiled `tools/bin/curtain.exe` and rebuilt `docs/` were invisible to `git status` for free, but only because `workspace/` happens to live nested inside the Canary repo's own root `.gitignore`. A site scaffolded by `canary init` somewhere else has no such parent file and would see its build output and any precompiled binaries show up as untracked clutter with nothing telling git to ignore them. `SiteInitializer` had never scaffolded a `.gitignore` at all.

**The first version shipped a real bug, caught immediately by the user rather than by any test.** It ignored `output.dir` unconditionally — which breaks the single most obvious deploy path a new Canary site would reach for, since `output.dir` defaults to `docs` *specifically* to match GitHub Pages' "serve from `/docs` on `main`" convention, a convention that requires the directory to actually be committed. The report was fast and specific:

> "hey, so i noticed the output directory got added to .gitignore, this is bad for alot of workflows, a githib pages site for example"

It's the same class of mistake Act 19 already made and fixed once, in a different file: that Act's own `.gitignore` carve-out (`docs/` / `!/docs/`) exists precisely because a blanket ignore rule had almost swallowed `docsite`'s real, needs-to-be-committed build output. Four Acts and one rename later, the identical shape of bug reappeared in a *new* `.gitignore` — this time one Canary itself hands to every site it scaffolds, not just its own. Fixed the same way in spirit: `output.dir` is no longer actively ignored by default, shown instead as a commented-out opt-in line with an explanation, for the real minority case (a separate deploy branch, `canary publish`, a CI build step) where an author genuinely doesn't want build output in history.

**That work pulled in two more decisions that weren't originally on the table.** First, the scaffolded example tool got renamed from `example`/`tools/example.cs` to `curtain`/`tools/curtain.cs`, so a fresh site's own starter matches the name every doc example and the real dogfood sites already use, rather than teaching two different tool names for the same concept. Its `canary.jsonc` entry shows the new precompiled form commented out directly above the active plain-string line — demonstrating the feature without `canary init` itself ever needing to attempt an AOT publish (a design considered and rejected: it would turn `init` from a fast, always-succeeding file copy into something that can take 5-10 seconds and fail depending on whoever's machine happens to be running it).

Second — and bigger — showing that commented-out example meant `canary.jsonc` needed to actually tolerate comments, which it didn't; a `//` anywhere today was a hard parse failure. The conversation that followed went further than strictly necessary on purpose:

> "yes it does, and what about JSON5, it supports comments, I like the idea of canary config file being heavily commented as a way that makes things easier to onboard with"

Real JSON5 (unquoted keys, single-quoted strings) would have meant either a third-party parser of unverified AOT/trimming compatibility, or writing one from scratch — real scope for syntax sugar that doesn't actually serve the stated goal. What the goal actually needed was just comments and trailing commas, both already built into `System.Text.Json` (`JsonCommentHandling.Skip`, `AllowTrailingCommas`) with zero new dependencies. Settled quickly once framed that way, then immediately raised its own follow-on question — would VS Code flag every comment as a syntax error in a file still named `canary.json`? It would, since there's no in-file pragma for "treat this as JSONC" and VS Code goes by filename alone. The fix was a rename, `canary.json` → `canary.jsonc`, decided without much hesitation:

> "lets do 1, we are still in alpha so stability isint an expectation"

The same "pre-release doesn't need to protect a compatibility promise nobody's made yet" instinct that shipped the `{{checksum}}` placeholder removal in Act 13 and waved off the init-compat suggestion in Act 15, applied again to something with even more surface area — every `canary.json` reference across the codebase, both real dogfood sites' own config files, and every doc page that named it. Done as one pass: `CanaryJsonContext`'s new comment/trailing-comma options, `Program.cs`'s default `--config` path, `SiteInitializer`'s scaffolded filename, `workspace/canary.json` and `docsite/canary.json` renamed via `git mv` to keep their history, and every doc reference updated to match — deliberately *not* touching `devJournal.md`, `plan-archive/`, or `canary-readme-hn-critique.md`, on the same "the record should describe what was true when it was written" principle that kept `config.json` un-retconned in this very document back in Act 15.

**Writing the commented-out example itself hit its own small, real bug.** `JsonNode` has no concept of a comment, so the precompiled-form demo had to be spliced into the already-serialized JSON text as a plain string replace — and the first version of that splice silently no-op'd, producing a config with no comment in it at all, no error, nothing. The cause: the replace was anchored on an assumed `\n` line ending, but `System.Text.Json`'s indented writer actually emits `Environment.NewLine` (`\r\n` on Windows) — confirmed by reading the raw bytes of a real scaffolded file rather than guessing again. Fixed by building the anchor and replacement strings with `Environment.NewLine` instead of a literal `\n`.

One more small, honest thread from the same stretch of work: a diff turned up in `workspace/tools/curtain.cs` — a period changed to an exclamation point — that traced back to nothing done deliberately in this session. Reported plainly rather than silently reverted or silently kept:

> "That was me testing, revert it back to the period"

Reverted, the tool rebuilt from the restored source, and the build re-verified clean.

Verified end to end: a fresh `canary init` produces `canary.jsonc` (not `.json`) with both the active `curtain` line and its commented-out precompiled form intact, and `canary build` parses it correctly — comments included; a hand-edited `.gitignore` survives a `--force` re-init untouched; `output.dir` shows up only as a commented option, never as a live rule. 166 tests green throughout.

## Act 24: a second language for the toolchain, and what "guaranteed" actually means (Aug 25)

The last open thread from Act 23's renaming work: `canary init` scaffolded exactly one example tool, and it was C#. *"maybe we should think about adding a second example tool that isin't pre compiled written in something other than C#, is there anything thats (guarunteed to run) no matter the envoriment someone has set up, like python wouldnt work because they would need python"* — narrower than it first sounds, since Canary only targets Windows today, and the real question was which Windows-native options actually qualify as "no separate install, ever."

The list of candidates got shorter with each one checked rather than assumed:

- **Python, Node** — ruled out on sight, exactly as flagged: both need a runtime nobody's guaranteed to have installed.
- **Bash** — looked plausible at first (common enough on developer machines that this very session's own tool environment has it), but doesn't actually clear the bar: it's not a stock Windows component, only shows up via Git for Windows/WSL/Cygwin, and Windows has no built-in `.sh` file association at all — `ShellCommand.Resolve`'s `cmd.exe /c "call tools/foo.sh"` would fail outright without one of those already installed, worse than a graceful "not found."
- **Windows Script Host** (`cscript`/`wscript`, VBScript/JScript) — technically still present on many current Windows installs, but increasingly disabled by default in recent releases and one of the most commonly security-blocked LOLBins in managed environments. Correctly present, practically not a safe bet.
- **`cmd.exe` batch and Windows PowerShell 5.1** — the only two that are both genuinely universal (ship with every supported Windows version) and not actively being phased out or blocked.

Asked why batch specifically was a bad idea rather than just being told it was — *"why is batch bad? is it slow?"* — the honest answer was the opposite of the assumption: not slow at all, likely the fastest option on the table, since `cmd.exe` is a lightweight native binary with no interpreter/JIT warmup, unlike PowerShell's heavier startup or a JIT'd `dotnet run` tool (the exact overhead Act 22's whole feature exists to avoid). The real weakness is the language itself — brittle quoting and escaping (the same family of bug Act 22 had just spent real effort fixing), no real data structures, poor Unicode handling.

**A batch reading-time tool got built and verified anyway, on request, before the final call got made.** *"could you make a batch that did anything useful?"* — word-counting arbitrary markdown prose by tokenizing it through batch's own `for %%i in (...)` would reopen exactly the quoting landmine `ShellCommand.cs` already had two documented bugs in, so the working version sidestepped tokenizing prose entirely: redirect stdin to a temp file, read the file's *byte size*, and estimate word count from that (~6 bytes per English word) instead. Verified against real markdown deliberately salted with the exact characters that break naive batch parsing — `&`, `%`, parens, brackets — and it survived all of them, because none of that content was ever actually interpreted, only measured.

It worked, but the project already had a real, accurate, in-production PowerShell tool doing the same job better — `workspace/tools/reading-time.ps1`, live since Act 8, computing a true word count and inserting its badge in the semantically right spot instead of just appending one to the end. *"maybe powershell is the way to go and we just use reading-time.ps1"* — reusing proven code beat re-deriving an approximation in a language that fights back, and that's what shipped: `templates/default/tools/reading-time.ps1`, copied into every fresh scaffold alongside `curtain.cs`, registered but — same as `curtain` — not wired into any `.toolchain.json` by default, matching the "registration and application are separate, application is never automatic" rule from Act 6.

Verified live: a fresh `canary init` produces both tool files and both registry entries; manually wiring both into a scaffolded page's `.toolchain.json` and running `canary build` showed `reading-time` inserting a correct badge and `curtain` passing the page through byte-for-byte unchanged — confirmed as the correct, by-design outcome (its stderr proof-of-env-vars line is swallowed by `ToolchainRunner` on any successful run, only surfaced on failure), not mistaken for a bug. 166 tests green.

The 0.1.0 throughlines above kept holding, not just as history but as active predictions:

- **A mechanism that keeps needing bug fixes is a signal, not bad luck — confirmed a third time.** `ShellCommand.cs`'s cmd.exe-quoting fix, already revisited once for hooks (Act 8) and once for publish (Act 18), needed a third real fix for precompiled tools in Act 22 — not because the earlier fixes were wrong, but because each one had only ever been proven against the shapes of command already in the test suite, and a genuinely new shape (a bare, argument-less `.exe` path) tripped a corner none of them covered.
- **The same class of bug can recur in a new place even after it's been fixed once.** Act 19's `docs/` / `!/docs/` gitignore carve-out and Act 23's `output.dir` gitignore bug are the identical mistake — a blanket ignore rule swallowing a GitHub-Pages-served build output — caught the same way both times: by someone actually looking at what got ignored, not by a test.
- **Explicit still beats implicit, including when it costs real design effort to keep that way.** The commented-out precompiled-tool example in a fresh `canary.jsonc` exists specifically so `canary init` never has to guess whether a machine can do Native AOT publishing — it shows the option and lets the author flip it on deliberately, the same shape of choice as `!url` back in Act 3.
- **"We're still pre-release" is a standing license to make a bigger call than the immediate problem strictly requires, used on purpose, not by accident.** The `canary.json` → `canary.jsonc` rename touched far more surface area than "let one example comment parse correctly" needed — and got decided quickly anyway, on the same grounds Act 15's init-compatibility question and Act 13's `{{checksum}}` removal were.
